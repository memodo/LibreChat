# v0.8.7 Feature Adoption — Review & Decision List

**Purpose:** the v0.8.5 → v0.8.7-rc1 upgrade introduced a large batch of new features. This is a
**decision aid**, not a regression test (those live in `test-verification-015-m365-obo-v0.8.7.md`, Part C4).
For every notable v0.8.7 feature it records **what it is**, its **current state in *our* deployment**, **what
enabling it takes**, the **trade-off**, and a blank **Decision** column for you.

**Grounded in:** the deployed `librechat.yaml` (config schema `version: 1.3.6`) and what was directly
observed in the chat-test UI on 2026-07-13/14. Where a state couldn't be confirmed from config alone it is
tagged **⚪ verify** with how to check.

## How to read the state tags

- **🟢 ACTIVE** — on right now in our deployment; the decision is *keep / tune / communicate to users*, not on/off.
- **🟡 OFF — config only** — off, but enabling is a `librechat.yaml` edit (deploy via the yaml path: `git push` → prod `git pull` → `./prod.sh restart api`).
- **🔴 OFF — needs infrastructure** — a yaml flag alone isn't enough; a service must be stood up first.
- **⚪ VERIFY** — state needs a quick UI check to confirm.

**How agent capabilities are turned on:** most of the "agent" features below are toggled by adding the
capability string to `endpoints.agents.capabilities` in `librechat.yaml`. Today that array is:
`["file_search", "web_search", "actions", "artifacts", "tools"]`. The full v0.8.7 capability set is 16
(`file_search, web_search, artifacts, actions, tools, execute_code, subagents, skills, memory, chain,
context, ocr, hide_sequential_outputs, programmatic_tools, end_after_tools, deferred_tools`).

## Suggested first-pass recommendation (yours to override)

- **Keep** everything in **A** as-is; the only one worth a second look is **Global Memory `personalize: true`** — confirm it's acceptable from a data-minimization standpoint (it builds per-user profiles).
- **Quick wins to consider** from **B**: **file→context** (`context` — the whole-doc/OCR upload path, low risk; complements the RAG `file_search` you already run); **Agent Skills — instruction/knowledge modules** (`skills` — reusable playbooks, no sandbox needed); and optionally **multi-conversation**. Leave subagents/chain/memory-capability/marketplace/remote-agents **off** until a concrete need appears.
- **Basic Agent Skills is a B quick-win** (config-only). **Bundle only Code Interpreter + the *script-executing* subset of Skills** into a single future initiative (shared sandbox infra + security review) — don't hold basic Skills back for it.
- **Decide the cost-gauge policy (D)** after a quick UI check of what end users currently see.

> Deployment note: everything in B is a `librechat.yaml`-only change → yaml deploy path (`git push` → prod
> `git pull` → `./prod.sh restart api`), no dist rebuild. C requires new services and a separate rollout.

## Appendix — Agent Skills vs. Agents (basic, no code involved)

Both a basic skill and an agent are ultimately "instructions/knowledge for the model," so the difference is
about **modularity, reuse, and context economy** — not a new capability.

> An **agent** is *who the assistant is* — a persona (system prompt + model + tools) that is **always
> loaded**. A **basic skill** is a *reusable procedure/knowledge module* loaded **only when the task calls
> for it** (progressive disclosure: name + description advertised cheaply, full `SKILL.md` body primed on
> demand, `references/*` pulled only if needed).

| | **Agent** (Agent Builder) | **Basic skill** (`skills`, no code) |
|---|---|---|
| **Scope** | An identity/role ("Support Concierge") | A task/procedure ("process a warranty claim") |
| **Loading** | System prompt **always** in context, every turn | Only **name + description** always in context; **body loaded on demand** |
| **Reuse** | Instructions belong to that **one** agent | A standalone unit **many agents** can share (agent needs `skills_enabled: true`) |
| **Granularity** | One monolithic prompt | Many small modules; one agent can carry a whole library |
| **Layered knowledge** | Flat prompt; extra knowledge via `file_search`/RAG or context-attach | Two-level: catalog → body → `references/*`, each loaded only when needed |
| **Invocation control** | Always applies | Per-skill dial: manual `$`, always-apply, or model-decided (`disable-model-invocation` hides it from the model) |
| **Versioning / governance** | Edit affects that one agent | Versioned + separately permissioned; edit propagates everywhere it's used |

**When to use which:** put small, always-on, agent-specific guidance in the **agent prompt**; reach for a
**skill** when you have many procedures, want to reuse one across agents, want it applied only for the
relevant task, or want to version/govern it independently of any single agent.
