# RESEARCH-019-memory-write-fix

Diagnostic investigation (not greenfield feature research). Live root-cause debugging of a silent memory-WRITE failure on `chat-test.memodo.de` (v0.8.7-rc1 fork + M365, branch `feature/015-m365-obo-v0.8.7`).

## Symptom Recap

- READ/injection works: the memory context is loaded into every turn and older memories (12 May – 10 Jun 2026) are recalled correctly.
- WRITE is silently broken: the assistant replies "Noted and saved: …" (or equivalent), but no DB row is created, no "Updated saved memory" indicator renders, and **no error/warn is logged anywhere** for the attempt.
- Verified live: a fresh "remember I'm on Frontend team…" turn produced zero new rows; a later fresh chat could not recall it, but could still recall the old 12 May stored preference.

## System Data Flow

There are **two independent memory-write mechanisms** in the current codebase — this is a research finding not present in the original code map, and it materially changes the debugging surface:

1. **Post-turn ephemeral memory-agent extraction** (the mechanism the original code map targeted; pre-dates the v0.8.7 upgrade):
   - `useMemory()` — `api/server/controllers/agents/client.js:647-812`. Builds READ context (`getRequestMemories`, L676/800) and, when `isMemoryAgentEnabled(memoryConfig)` (L674, config helper at L540), builds a `prelimAgent` from `memoryConfig.agent` (L692-711 — for this fork's yaml, provider=`azureOpenAI`, model=`gpt-5-mini`, no explicit `id` → ephemeral branch L705-711), initializes it via `initializeAgent` (L730-753, endpoint resolved to `memoryConfig.agent?.provider` for the ephemeral id, L737-739), and on success builds `processMemory` via `createMemoryProcessor` (L782-797) and stores it on `this.processMemory`.
   - `runMemory(messages)` — L851-928. Early-returns if `this.processMemory == null` (`client.js:853-855`, plain `if (this.processMemory == null) { return; }`). Otherwise windows/truncates the chat buffer (`messageWindowSize`, `maxInputTokens` — added by upstream #13606, 2026-06-09) and calls `this.processMemory([bufferMessage])` (L924).
   - Invocation: `memoryPromise = this.runMemory(memoryMessages)` fired inside `runAgents` (L1541-1542), **concurrently** with the main `createRun`, not blocking the visible response.
   - Resolution: `await this.awaitMemoryWithTimeout(memoryPromise)` in the `finally` block of `chatCompletion` (L1720), 3-second timeout (L622-642, timeout logs `logger.warn`). This runs and completes (or times out with a warning) **before** `client.js`'s `chatCompletion()` promise resolves.
   - `cleanup.js:270-272` nulls `client.processMemory` — but only after `disposeClient(client)` is called in `request.js` (multiple call sites, e.g. L699/788/864/882/918/945/1045), which is only reached after `await sendPromise` (`request.js:612`) — i.e., after `chatCompletion()`'s own `finally` (including the `awaitMemoryWithTimeout` await) has already completed. **The originally-hypothesized cleanup race is not supported by the code**: `processMemory` is awaited (with a 3s backstop) strictly before it can be nulled.
   - Actual DB write: `packages/api/src/agents/memory.ts` `processMemory()` (L647-872) builds `memoryTool`/`deleteMemoryTool` (L681-692), runs a `Run.create` "standard" graph with those two tools bound (L825-837), executes `run.processStream` (L854), and a `tool_end` callback (`createMemoryCallback`, L979-1000 → `handleMemoryArtifact`, L928-969) is what actually surfaces a written memory as an SSE `attachment` event **and** is the only place `artifactPromises` gets populated. If the model never calls `set_memory`/`delete_memory`, `artifactPromises` stays `[]`, `Promise.all([])` resolves to `[]`, nothing is pushed to `this.artifactPromises`, and the turn completes with **zero errors, zero warnings, zero indicator** — a completion that looks identical, from the logs, to "nothing to remember this turn."

2. **Inline memory-as-agent-capability tools** (NEW upstream mechanism, landed via `397ddc536` "Add Memory as an Agent Capability with Inline Tools and Ephemeral Badge", 2026-06-24 — explicitly documented in its own commit message as **"Additive to and independent of the existing post-turn memory extraction agent"**):
   - Gated by `endpoints.agents.capabilities` containing `"memory"` in `librechat.yaml` (confirmed present: `librechat.yaml:226`, alongside `chain`/`skills` — matches the 2026-07-14 "agent capabilities memory+chain+skills live" adoption decision).
   - `agentHasInlineMemoryTools(agent)` (`memory.ts:446-461`) detects whether the *running* agent (which, for a plain "GPT-5, not a saved agent" chat, is the **ephemeral agent** built from the per-message `ephemeralAgent` body flag, ` TEphemeralAgent.memory`) has `set_memory`/`delete_memory` bound as real tools — via `agent.memoryToolsRegistered` or a `Tools.memory` marker in `agent.tools`.
   - `isMemoryToolAllowed` (`memory.ts:504-537`) re-checks the full gate (capability present, memory configured/not opted out, `MEMORIES.USE`+write permissions) at tool-execution time, independent of registration time.
   - `buildInlineMemoryTool` (`memory.ts:545-621`) is what actually constructs the bound `set_memory`/`delete_memory` `DynamicStructuredTool` instances for the primary chat agent.
   - **This is very likely the mechanism the user's "Use memory" composer toggle and the tutorial's "Updated saved memory" indicator refer to** (see Tutorial Impact) — i.e., the user was expecting a *visible*, foreground tool call on the primary GPT-5 turn (comparable to M365's "Ran get-current-user" or Skills' "Used 2 tools"), which is exactly what this new mechanism is designed to produce when it fires, and exactly what did **not** appear.
   - This is a large, multi-round feature (the commit body records 4 separate "Address Codex review" follow-up patches for gating/validKeys/permission bugs) — a classic shape for a residual edge case, and the commit explicitly calls out **"Adds the ephemeral path (`TEphemeralAgent.memory`, load/added agent tool injection)"** as a distinct code path from the saved-agent path — i.e. the exact scenario in this repro (plain ephemeral GPT-5 chat, not a saved agent).

Both mechanisms terminate in the same DB write primitives (`db.setMemory`/`db.deleteMemory` → `memoryentries` collection), so a failure of *either* looks identical from the user's seat: an unfulfilled promise to remember, with no visible tool call and no DB row. **This is resolved, not an open ambiguity**: the regression is in mechanism 1 (post-turn). See "Root Cause Analysis — H1/H2 Resolution" below for why mechanism 2 (inline) is eliminated as the cause of the reported symptom, independent of and prior to any live repro.

### Why READ still works

`useMemory()`'s `getRequestMemories` (context load, L676-681 non-agent path, L800-804 agent path) is independent of the write mechanisms above — it purely formats existing `memoryentries` rows into the system-context block (`memoryContext`/`keyedMemoryContext`, L536-537) applied to every agent via `applyContextToAgent` (L601-611). It has no dependency on `processMemory`, the inline tools, or any LLM tool call — it is a straight DB read + template, which is why recall of the pre-06-10 entries continues to work even though no *new* entries can land.

## Root Cause Analysis

### H1/H2 Resolution (revised 2026-07-22, post-critical-review)

**RESOLVED: the regression is in mechanism 1 — the post-turn ephemeral gpt-5-mini memory-agent path (H1).** An earlier draft of this document presented H1 (post-turn silent no-op) and H2 (the new inline memory-capability mechanism, `397ddc536`/PR #13869, 2026-06-24) as co-equal, statically-indistinguishable hypotheses. A critical review (`SDD/reviews/CRITICAL-RESEARCH-memory-write-fix-20260722.md`, Finding 1) correctly identified this as confirmation-bias framing: the evidence to eliminate H2 as the *regression* cause was already gathered in this document and did not require a live repro to apply. Two independent, verified reasons:

1. **Timing.** All 14 existing `memoryentries` rows (newest `updated_at` 2026-06-10T14:02:09Z) predate `397ddc536` by two weeks (that commit landed 2026-06-24). H2's code did not exist when the last successful write happened. A mechanism cannot cause the regression of behavior that stopped working before the mechanism was written.
2. **Toggle gate.** H2 only registers inline `set_memory`/`delete_memory` tools when **both** (a) the run-level `memoryAvailable` gate holds and (b) the *running agent's* tool list carries the `Tools.memory` marker. For an ephemeral (non-saved-agent) chat, that marker is pushed **only** when the per-turn "Use memory" composer toggle is on — verified directly in source:
   - `packages/api/src/agents/added.ts:184-185`: `if (ephemeralAgent?.memory === true || modelSpec?.memory === true) { tools.push(Tools.memory); }`
   - `packages/api/src/agents/load.ts:76-77`: identical gate for the `load` ephemeral path.
   - `packages/api/src/agents/initialize.ts:1102-1104`: `const agentRequestsMemory = (agent.tools ?? []).includes(Tools.memory); const inlineMemoryRegistered = params.memoryAvailable === true && agentRequestsMemory;` — inline registration additionally requires the per-agent marker, not just the run-level capability gate.

   The repro described in this investigation is a plain "GPT-5, not a saved agent" chat with no mention of the "Use memory" toggle being enabled. Under the gate above, `ephemeralAgent?.memory` is `undefined`/`false` by default, so `Tools.memory` is never pushed, `agentRequestsMemory` is `false`, and `inlineMemoryRegistered` is `false` — **H2 does not even register for this repro**, let alone execute. It is not merely "unconfirmed as active," it is structurally inactive for the described symptom.

**Consequence:** H2 (inline memory-as-capability) is downgraded from "co-equal unconfirmed mechanism" to **a separate, lower-priority, toggle-gated track that may never have worked in this fork but is not implicated in the reported regression**. It should be verified independently (toggle ON) at some point, but it is off the critical path for the pre-cutover fix. All root-cause work below is scoped to H1.

### Evidence caveats (added per critical review Findings 4, 5, 8 — read honestly, not re-verified live)

This document repeatedly cites "absent from 72h of logs" to rule out or downweight several hypotheses (cleanup race, ephemeral-agent init failure, swallowed exceptions). The critical review (Finding 4) correctly flagged that the exact grep pattern, log level, rotation window, and whether the resumable-stream (`GenerationJobManager`) path was covered were never recorded in the original pass, making this the weakest load-bearing evidence in the document. **Honest accounting, not re-verified in this revision pass** (this pass is local-source-only, no box access per the hard constraint): the "72h, zero matches" claim was gathered during the live chat-test investigation as a general `docker logs` scan for `memoryagent`/`memory`/`error`/`warn` tokens, not a level-by-level, path-by-path audit. **Treat it as corroborating, not load-bearing** — it is consistent with the silent-no-op hypothesis but does not, on its own, rule out a swallowed exception at a log level or code path the scan didn't cover. The Runtime Verification Plan below specifies the exact grep this claim should be re-run against before it is relied on for the go/no-go decision.

Similarly, the "Live DB Check (Authoritative)" query above (critical review Finding 5) filters to a single `userId` and generalizes to "the write path is broken" globally. That generalization is a reasonable inference — `useMemory()` gates only on `Permissions.USE` (`client.js:652-657`), and the post-turn write tools are built without any additional per-user write-permission re-check (`memory.ts:681-692`), so a per-user/role permission regression would most plausibly also break READ, which is confirmed still working — but it is an inference, not a directly-verified global fact. The Runtime Verification Plan below adds a `countDocuments` sweep across all users to close this gap.

Candidate causes for the H1 (post-turn) regression, each evaluated against source, git history, and the live DB/log evidence:

### 1. Cleanup race — `client.processMemory` nulled before `runMemory` resolves
**Against:** `awaitMemoryWithTimeout(memoryPromise)` runs inside `chatCompletion`'s own `finally` block (`client.js:1719-1723`) and is on the critical path of the promise `request.js` awaits (`sendPromise`, L612) before any `disposeClient(client)` call (L699/788/864/882/918/945/1045) is reached, and `cleanup.js:270-272` only nulls `processMemory` on an already-disposed client. The 3-second timeout is itself a backstop that would still log `logger.warn('[AgentClient] Memory processing timed out after 3 seconds')` (L636) — no such line appears in 72h of logs. **Ruled out** as the active cause (though it remains a latent risk if a future change breaks the ordering).

### 2. Ephemeral-agent early return skips `runMemory` entirely
**Against:** `useMemory()`'s ephemeral branch (`prelimAgent = { id: EPHEMERAL_AGENT_ID, ...memoryConfig.agent }`, L710) is exactly the branch this fork's yaml hits (`memoryConfig.agent.id` unset, `model`+`provider` set). `initializeAgent` failing would log `'[api/server/controllers/agents/client.js #useMemory] No agent found for memory'` (L756-760, `logger.warn`) — absent from 72h of logs. **Not confirmed as the active cause** from available evidence, though it cannot be fully excluded without a live trace (`initializeAgent`'s internals — Azure credential/deployment resolution for the ephemeral agent path — were not read in this pass; see Runtime Verification Plan).

### 3. Azure env-var leak (legacy `AZURE_OPENAI_ENDPOINT`/`AZURE_OPENAI_API_KEY` misrouting to Switzerland, 401)
**Against:** Confirmed live — `docker exec LibreChat printenv` shows both vars **empty** on chat-test. If the vars are empty, the leak mechanism cannot fire regardless of code path — this is the primary, sufficient evidence and **ruled out on its own**. The secondary argument in the original pass ("title generation works, same model, therefore memory routing is fine") is weaker than presented (critical review Finding 8): it assumes title-gen and the memory agent resolve Azure credentials via identical paths, which was not independently traced (the memory agent uses `initializeAgent` with `endpointOption.endpoint = memoryConfig.agent.provider`, `client.js:737-739`, a distinct ephemeral-agent branch from title generation's). Treat the equivalence argument as illustrative, not evidentiary — the empty-env-var check alone is what rules this out.

### 4. Model produces no tool call (silent no-op, not an error)
**For:** This is the only hypothesis consistent with *every* observed data point simultaneously: (a) no error/warn logs surfaced for the repro window despite active use (method caveat below), (b) the DB write primitive (`setMemory`) is only ever invoked from a `tool_end` callback (`memory.ts:979-1000`) — no tool call, no callback, no write, no exception, (c) `Promise.all([])` on an empty `artifactPromises` array is a **successful**, silent resolution (`processMemory`, `memory.ts:865`), (d) the assistant's "Noted and saved" text is generated by the *primary* chat model narrating what it believes happened, not gated on the post-turn agent's actual outcome (the primary turn and the post-turn extraction are on separate LLM calls entirely — the primary model has no way to know whether the background extraction succeeded), (e) title generation (same model/provider) working confirms Azure routing/credentials are fine in general, so the fault is specific to the memory tool-calling path, not general model/endpoint health. Now the **leading hypothesis by elimination**: §5 below traces the two commits originally suspected of causing this behavior (`397ddc536`, `8fc231420`) directly and finds neither alters the H1 write path for this repro's shape (a short, fresh chat) — narrowing, not just leaving unconfirmed, the space this hypothesis has to share with a code-level regression. Confirming it fully still requires either DEBUG_LOGGING (to see `[MemoryAgent] Processed successfully` / `Returned no content`, both currently emitted at `logger.debug`, below the default log level) or live network/transcript inspection during a real repro (see Runtime Verification Plan) — **or** one further static read (§5, "open lead") that could close it without any live session.

### 5. Static trace of the three candidate regression-window commits (this pass, 2026-07-22)

The regression window is bounded by two facts established above: the post-turn path last wrote successfully on 2026-06-10 (pre-merge code), and the v0.8.5→v0.8.7-rc1 upstream merge (`1d6c927e2`, 2026-06-22) is the first point at which any upstream memory-processing change reached this fork. Per the critical review's Finding 2 ("`397ddc536` mischaracterized as additive/independent — diff it"), the highest-value action was to actually diff the candidate commits against the live H1 write path (`useMemory` → `processMemory` → `Run.create` → `tool_end` → `handleMemoryArtifact` → `db.setMemory`) rather than reason from commit messages. Three commits were traced; the result **narrows but does not yet fully close** the H1 root cause:

**a. `397ddc536` (2026-06-24, "Add Memory as an Agent Capability…", the commit originally flagged as H2) — ELIMINATED as the H1 code-level cause.**
Its own commit message ("Additive to and independent of the existing post-turn memory extraction agent") is imprecise about *file scope* — it does touch two files the post-turn path shares — but tracing what it actually changed in those files shows no behavioral effect on a normal post-turn write:
- `git show 397ddc536 --stat -- packages/api/src/agents/memory.ts` shows +430/−69 lines, but `grep -n "processMemory\|createMemoryProcessor\|handleMemoryArtifact\|createMemoryCallback\|Run.create\|processStream"` against the diff returns **zero matches**. Every changed line is confined to `createMemoryTool`/`createDeleteMemoryTool` (the two tool *factories*, shared by both mechanisms — refactored to serialize writes and add key/char-length guards, but the core `validKeys` check → `setMemory()` call → success/failure return is preserved unchanged for the non-limit-exceeded case) plus wholly new, appended functions (`agentHasInlineMemoryTools`, `isMemoryToolAllowed`, `buildInlineMemoryTool`, `getRequestMemories`) that H1 never calls. `processMemory`, `createMemoryProcessor`, `Run.create`, and `handleMemoryArtifact`/`createMemoryCallback` are byte-for-byte untouched by this commit.
- `git show 397ddc536 -- api/server/controllers/agents/client.js`: `useMemory()` is refactored to return `{withKeys, withoutKeys}` instead of a bare string, and — in the memory-agent-enabled branch — a new `getRequestMemories()` call is added **after** `this.processMemory = processMemory;` (client.js:786, pre-existing assignment line, unmoved) to fetch the keyed context, wrapped in its own try/catch that falls back to `withKeys = withoutKeys` on error and only `logger.error`s. This new code cannot prevent or delay the `this.processMemory` assignment (it runs strictly after), and cannot throw past its own catch, so it cannot explain `runMemory`'s early return or a swallowed exception in the write path. The `prelimAgent`/`initializeAgent`/`createMemoryProcessor` construction block (client.js ~665-771, matching this doc's L692-797 map) has **no diff hunk at all** in this commit — confirmed untouched.
- `git show 397ddc536 -- api/server/controllers/agents/callbacks.js`: adds a **new**, purely additive `if (output.artifact[Tools.memory])` branch to `createToolEndCallback` (the *primary* agent's tool-end handler, used for inline tool calls) — a different callback from `processMemory`'s own standalone-Run `createMemoryCallback` in `memory.ts`. Does not touch H1.
**Verdict: `397ddc536` is cleared as the cause of the H1 regression for this repro.** The Fix Options below no longer target it.

**b. `8fc231420` (2026-06-09, "Bound Memory Agent Input", #13606, the commit the original doc waved off with "diff looks correct") — ELIMINATED for this specific repro, on stronger evidence than the original dismissal.**
The critical review (Finding 3) correctly flagged the original one-line dismissal as under-evidenced given this commit added the `runMemory` windowing/truncation logic. Tracing the current source (`api/server/controllers/agents/client.js:851-928`) confirms:
- The message-window re-anchoring logic (`client.js:869-882`, requiring the window to start on a `role === 'user'` message) only executes `if (chatMessages.length > messageWindowSize)` (default `messageWindowSize = 5`, `client.js:858`). A fresh chat with a single "remember X" turn has 1-2 messages in the buffer, never exceeding 5 — **the windowing branch does not execute at all for this repro's shape.**
- The char/token truncation added by this commit (`client.js:886-911`) truncates only when `bufferString.length > maxInputTokens * 8` chars, with `maxInputTokens` defaulting to `DEFAULT_MEMORY_MAX_INPUT_TOKENS = 12000` (`packages/data-provider/src/config.ts:1732`) — a ~96,000-character budget. A short single-turn chat is orders of magnitude under this, and `processTextWithTokenLimit` is called with `preserve: 'end'` (keeps the most recent content, i.e. the last-typed instruction, when truncation *does* occur for long chats).
**Verdict: `8fc231420` is cleared as the cause for the exact repro described** (a fresh, short "remember X" chat). It remains a live concern only for long-running chats that exceed the window/token budget — worth a regression test, not a fix, for this specific bug.

**c. `1b79e0b78` ("Align LibreChat With Agents LangChain Upgrade", #12922) — CLEARED (2026-07-22, Option A0 static trace, no runtime).**
This commit adds `normalizeMemoryLLMConfig()` (`memory.ts:61-67`): `if (typeof config.apiKey !== 'string') { delete config.apiKey; }`, applied to the memory agent's `finalLLMConfig` (`memory.ts:717-719`). Option A0 traced the *entire* chain that populates `llmConfig` for the ephemeral memory agent, end to end, and finds this is **not the cause**:
  - `useMemory()` builds `llmConfig = Object.assign({provider: agent.provider, model: agent.model}, agent.model_parameters)` (`client.js:763-769`) **after** `agent = await initializeAgent(...)` (`client.js:730-753`) has already run.
  - `initializeAgent` (`packages/api/src/agents/initialize.ts:1175`) **overwrites** `agent.model_parameters` with `{ ...options.llmConfig }`, where `options` is the return of `getOptions()` — the exact same provider-resolution function (`getProviderConfig({provider, appConfig}).getOptions`, `initialize.ts:993-1011`) used to initialize **every** azureOpenAI agent in this codebase, including the primary tool-bearing chat agent (`isInitialAgent = true`) — there is no memory-specific credential-resolution branch. For `azureOpenAI` this resolves to `initializeOpenAI` (`packages/api/src/endpoints/openai/initialize.ts`).
  - `initializeOpenAI` resolves `apiKey`/`azureOptions` via `mapModelToAzureConfig({modelName: 'gpt-5-mini', modelGroupMap, groupMap})` (`initialize.ts:91-127`), sourced from `librechat.yaml`'s `azureOpenAI.groups[].apiKey` (this fork: `${AZURE_OPENAI_API_KEY_SWEDEN}`, a static string, confirmed **present and non-empty** in the live box's `/app/.env`, read-only via `ssh memodo-eng-test`; the `docker exec printenv`-visible, *deliberately emptied* `AZURE_OPENAI_API_KEY`/`AZURE_OPENAI_ENDPOINT` are a distinct legacy pair per `project_azure_endpoint_env_leak` and irrelevant to per-group credential resolution).
  - `getOpenAILLMConfig` (`packages/api/src/endpoints/openai/llm.ts:751-798`) then builds the returned `llmConfig`. For the **standard (non-Responses-API) Azure branch** — which is what this fork's memory-agent config resolves to, since `memory.agent.model_parameters` (`temperature: 0.1` only) never sets `useResponsesApi` — the function does **not** set `llmConfig.apiKey` at all; instead `Object.assign(llmConfig, updatedAzure)` (line 780) sets `llmConfig.azureOpenAIApiKey`, `azureOpenAIApiInstanceName`, `azureOpenAIApiDeploymentName`, `azureOpenAIApiVersion`, `azureOpenAIBasePath` as **plain string** top-level fields. `llmConfig.apiKey` is only ever set (also as a string) in the `!azure` branch (line 752) or the Responses-API sub-branch (line 792) — neither of which applies here.
  - **`normalizeMemoryLLMConfig` only inspects/deletes `.apiKey`.** It never reads or touches `azureOpenAIApiKey`/`azureOpenAIApiInstanceName`/`azureOpenAIApiDeploymentName`/`azureOpenAIApiVersion`. In this fork's standard-Azure-branch shape, `.apiKey` is simply absent from the object to begin with (a no-op delete of a key that was never set), and all the fields that actually carry the credential and routing info pass through `normalizeMemoryLLMConfig({...})` completely untouched.
**Verdict: CLEARED.** The memory agent's azureOpenAI apiKey/instance/deployment/version reach `Run.create`'s `finalLLMConfig` exactly as resolved by the shared, already-proven-working `initializeAgent`→`getProviderConfig`→`initializeOpenAI`→`getOpenAILLMConfig` chain — the identical code path used by the primary chat agent. `normalizeMemoryLLMConfig` cannot be, and is not, silently stripping the memory agent's credentials in this deployment.

**Net effect on root-cause confidence:** all three candidate 06-22-merge commits touching memory-adjacent code (`8fc231420`, `397ddc536`, `1b79e0b78`) have now been directly traced and **cleared** as the H1 code-level cause for this repro's shape. Config/credential resolution (Option A0) is fully closed: the memory agent's LLM call is correctly authenticated and configured. This leaves **"model completes with no `set_memory` tool call" (§4, silent no-op) as the sole remaining explanation**, together with the narrow residual question of *why* gpt-5-mini declines to call the tool for this repro (prompt/instruction framing, tool-binding for the standalone `Run.create` graph, or a `disableStreaming`/`maxRetries: 0` interaction) — none of which is discriminable without a live observation. **Root-cause status: static investigation is exhausted and CLOSED — every static/code lead has been traced to a verdict (cleared or confirmed-inactive); the remaining gap is irreducibly runtime-only (Option A1).**

### Regression window (git evidence, revised)
This fork's memory-write path last succeeded under **pre-upgrade (v0.8.5-era) code** — the newest DB row is 2026-06-10.
