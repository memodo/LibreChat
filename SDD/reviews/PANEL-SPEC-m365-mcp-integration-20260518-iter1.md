# Spec Review Panel: M365 MCP Integration (SPEC-014)

**Date:** 2026-05-18
**Spec reviewed:** SDD/requirements/SPEC-014-m365-mcp-integration.md
**Research context:** SDD/research/RESEARCH-005-m365-mcp-integration.md (substantive); SDD/research/RESEARCH-014-m365-mcp-integration.md (pointer stub)
**Panel:** security, performance, api-contract, module-depth, privacy, reliability

## Executive Summary

SPEC-014 deploys Softeria's `@softeria/ms-365-mcp-server` as a stateless Docker sidecar and wires it to LibreChat's existing BYOT/OBO Graph token plumbing. The architecture is well-anchored in existing code (REQ-007 reuses `GraphTokenService`, REQ-019 reuses SPEC-009 PII detection, REQ-011 reuses internal-only network exposure), but the panel surfaced **9 HIGH, 11 MEDIUM, 6 LOW findings after dedup** (down from 31 raw across specialists) clustered around four standout concerns. **First**, the supply-chain posture is unsafe: REQ-002 and OD-1 ship `@latest` to first production deploy with no integrity hash, no SBOM, no sub-processor record (Security HIGH + API-Contract HIGH + Privacy HIGH overlap). **Second**, the sidecar is a single-point custodian of every signed-in user's Graph access token in flight, yet REQ-004's smoke test §6 literally greps for `Bearer eyJ...` in `mcp-m365` logs — confirming token-in-logs is the *expected* state, not a violation (Security MEDIUM + Privacy MEDIUM). **Third**, Phase-1 scopes (REQ-008) include `Files.Read.All` and `Sites.Read.All` — tenant-wide read, not user-scoped — violating least privilege and breaking the spec's own "read-only blast radius" claim (SEC-003). **Fourth**, REQ-014's "restart-only deploy" combined with PERF-003's in-memory OBO cache produces a deterministic thundering herd on Entra after every API restart, with no single-flight protection (Performance HIGH + Reliability HIGH overlap). Genuinely surprising: a privacy specialist surfaced four HIGHs around GDPR (Art. 28 sub-processor disclosure, Art. 26 controller/processor role, Art. 5(1)(e) retention, Art. 15/17 DSR flow) that no other reviewer would have caught — the spec treats this as a config-and-image exercise, but it is materially a personal-data ingestion path with no governance scaffolding.

## Verdict

**STOP AND RECONSIDER**

Nine HIGH findings across five of the six specialists (and one MEDIUM module-depth finding adjacent to the security/privacy cluster) make this spec not safe to implement as written. The privacy HIGHs alone (sub-processor disclosure, controller/processor role determination, retention, DSR) are blocking under GDPR Art. 28/26/5/15/17 for any production rollout in the EU tenant. The security HIGHs (supply-chain unpinned, token over-scope) and the reliability HIGHs (start-ordering, OBO thundering herd, single-point hung-but-up failure) are independently sufficient to require revision. The performance HIGHs (tail-latency budget absent, OBO stampede) overlap with reliability and amplify the operational risk surface. This is not a "fix three things and proceed" set of findings — the spec needs a second pass that adds an information-governance subsection, hardens the supply chain, narrows scopes, defines the Bearer token contract and error shape, and introduces real readiness/health/single-flight semantics. The module-depth review separately flagged that MODULE-002's `low` risk tier under-allocates downstream review attention given that it owns the only PII handoff path; that re-tiering should land in the same revision.

## Findings by Specialist

#### Security Findings

- **HIGH** Confused-deputy / token replay risk at BYOT trust boundary unaddressed
  - Evidence: MODULE-001 "Hides" bullet 3 ("the contract is BYOT-only") and "Risk" paragraph ("the only LibreChat-adjacent process touching every user's Graph data, even transiently"); SEC-001 ("no tokens at rest"); REQ-006 ("pure BYOT mode"). The spec acknowledges every user's Graph token transits the sidecar but defines no defense if `mcp-m365` is compromised (replay against `graph.microsoft.com` from off-host, exfil over outbound TLS, in-process memory dump). The Hetzner Cloud Firewall is described as inbound-only (REQ-011); egress to `graph.microsoft.com` is implicitly unrestricted (SEC-005 documents the outbound but does not constrain it).
  - Risk: A compromised image (supply-chain attack on `@softeria/ms-365-mcp-server@latest` per REQ-002/OD-1, or an `npm install` transitive) gains a stream of short-lived but live user Graph tokens and can call Graph from anywhere outbound 443 is reachable. Phase-1 read-only scopes (SEC-003) bound the blast radius to read access across every signed-in user's mail, files, calendar, contacts, notes, tasks.
  - Resolution: Add a SEC-006 requirement enumerating sidecar hardening: (a) replace `@latest` with a version + integrity hash before first prod deploy (tighten OD-1 from "after first successful deploy" to "before first prod deploy"), (b) run the container as non-root with a read-only root filesystem and `no-new-privileges`, (c) constrain egress to `graph.microsoft.com:443` only via an explicit Docker network policy or outbound allowlist (currently only inbound is constrained per REQ-011), (d) document the residual replay window equal to Graph access-token TTL and the detection signal (Graph sign-in logs showing token use from an unexpected IP).
  - [Cross-flagged by privacy (Sub-processor disclosure HIGH) and api-contract (Tool-call contract drift HIGH) as the same supply-chain root cause.]

- **HIGH** Token over-scope: `Sites.Read.All` and `Files.Read.All` exceed least privilege
  - Evidence: REQ-008 grants `Files.Read.All`, `Sites.Read.All`, `Notes.Read.All`, `Contacts.Read`, `Tasks.Read`, `Mail.Read`, `Calendars.Read`. Phase-1 stakeholder text (Stakeholder Validation, Security/Compliance bullet) says "read-only" but does not justify tenant-wide read. `Files.Read.All` grants read across every site/drive the user can access (including delegated tenant-wide content), not just `/me/drive`. `Sites.Read.All` is tenant-wide; `Sites.Selected` is the least-privilege alternative.
  - Risk: A compromised sidecar (see HIGH above) or a prompt-injection in an M365 document immediately exfiltrates anything the user can read across the tenant, not just their own OneDrive. The blast radius is "everything the user has SharePoint access to," which for any privileged user is large.
  - Resolution: In REQ-008, replace `Files.Read.All` with `Files.Read` (user's own files) and replace `Sites.Read.All` with `Sites.Selected` plus an explicit list of sites in scope; if `Sites.Selected` is operationally infeasible for phase-1, add a written rationale to REQ-008 and SEC-003 explaining why tenant-wide read is required and what compensating control bounds it.

- **MEDIUM** Sidecar log surface may capture Bearer tokens [also flagged by privacy as "Sidecar log content is unspecified"]
  - Evidence: OPS-002 ("logs to stdout/stderr ... no volume mounts"); REQ-004 sets `Authorization: "Bearer {{LIBRECHAT_GRAPH_ACCESS_TOKEN}}"` on every call; Verification Plan smoke test 6 explicitly greps for inbound `Authorization: Bearer eyJ...` in `docker compose logs -f mcp-m365` — confirming the token is presumed visible in container logs. Anti-pattern: "Logging that leaks secrets or PII."
  - Risk: Graph access tokens land in `docker compose logs`, in any centralised log shipper added later, and in `./prod.sh logs` output (operator-visible). Any operator with shell on the prod host or read access to log aggregation harvests live user Graph tokens. Privacy specialist additionally notes Graph URL query strings, mail subjects, attendee emails, and file names also at risk if Softeria's default log level is verbose.
  - Resolution: Add a SEC-007 requirement: the sidecar must not log request `Authorization` headers, request bodies, or response bodies at the default log level. Either (a) verify upstream `@softeria/ms-365-mcp-server` redacts headers and document the verified version, or (b) front the sidecar with a minimal proxy / log filter that strips `Authorization`. Change Verification Plan smoke test 6 to assert tokens are NOT present in `mcp-m365` logs (negative assertion), and instead confirm BYOT plumbing from the LibreChat side. Combined with privacy specialist's payload-leak resolution: also forbid logging URL query strings beyond path templates, mail subjects, recipient addresses, file names, attendee identifiers.

- **MEDIUM** `mcpSettings.allowedDomains` hostname-only entry is a soft boundary [also flagged by api-contract as "Bare hostname is a low-grade contract weakness"]
  - Evidence: REQ-005 / OD-2 specify a bare-hostname entry `mcp-m365`; `extractMCPServerDomain` returns origin, `isDomainAllowedCore` matches hostname-only. The allowlist does not pin scheme, port, or network. Auto-memory note "mcpSettings.allowedDomains semantics" confirms a non-empty allowlist is strict — but the strictness is hostname-only.
  - Risk: An admin (or a misapplied config patch) adding any other MCP entry that resolves to a host literally named `mcp-m365` on any port over any scheme would pass `isMCPDomainAllowed`. More realistically, a future user-created MCP entry with URL `http://mcp-m365:<other-port>/...` would be accepted; if the sidecar later exposes any additional listener (debug, metrics), it becomes reachable. Hostname-only allowlisting is a weaker control than scheme+host+port.
  - Resolution: In REQ-005 / OD-2, change the allowlist semantics to `http://mcp-m365:3000` (scheme+host+port). If `isDomainAllowedCore` cannot match a scheme+port entry today, file that as a follow-up dependency in Open Decisions and gate REQ-005 on it. Additionally, document that the sidecar must `EXPOSE` only port 3000 and bind no other listeners (tighten REQ-002).

- **MEDIUM** SEC-004 audit-reconstruction mechanism is hand-wavy and not testable [also flagged by privacy as "Audit-reconstruction claim risks logging request/response bodies"]
  - Evidence: SEC-004 "Each Graph call is attributable to a single Entra user via the JWT-bearer OBO exchange; LibreChat conversation logs + Graph activity logs together produce a per-user trail." No correlation identifier (e.g., `client-request-id` / `request-id` header propagation from LibreChat through the sidecar to Graph) is specified. The Verification Plan has no test that takes a Graph audit-log entry and walks back to a LibreChat conversation+user.
  - Risk: In an incident (token replay, anomalous Graph access), responders cannot deterministically map a Graph sign-in log entry to a specific LibreChat user+conversation+tool-call. The trail exists in principle (OBO ties tokens to `user.openidId`) but not as a reproducible procedure. Privacy specialist further notes that conflating "conversation logs" with "audit logs" mixes lawful bases and retention requirements — the audit record should be minimal metadata, not the conversation body.
  - Resolution: Tighten SEC-004 to specify: (a) LibreChat sets a per-tool-call correlation header on the outbound MCP request (e.g., `client-request-id: <conversation-id>:<message-id>`), (b) the sidecar forwards or maps that header to Graph's `client-request-id`, (c) verification adds a test that issues one tool call and confirms the same correlation ID appears in LibreChat logs, `mcp-m365` logs, and a Graph activity-log query. Additionally per privacy: define audit record as `(timestamp, user.openidId, tool name, scope, Graph endpoint path template, HTTP status code)` — explicitly excluding bodies, query-string filters, and recipient identifiers. Reconstruction is `LibreChat metadata` ⋈ `Graph activity log` keyed by Entra user.

- **LOW** Phase-1 OAuth supply-chain pinning gap [also flagged by api-contract as "Tool-call contract drift via unpinned Softeria image" HIGH and privacy as "Build-time supply-chain" LOW]
  - Evidence: REQ-002 + OD-1 install `@softeria/ms-365-mcp-server@latest`, pin "after first successful deploy." The first prod build pulls a floating tag.
  - Risk: A malicious or compromised release between local smoke-test and prod build hits production. Anti-pattern: cryptographic primitives / supply chain without rationale. **Severity elevated to HIGH after dedup** given api-contract reviewer's independent flag that contract drift (renamed tools, changed argument schemas) is invisible to LibreChat with no version pin.
  - Resolution: Tighten OD-1 — pin to a specific version + npm `--integrity` hash (e.g., `npm view <name>@<version> dist.integrity`) recorded in `mcp-m365/Dockerfile` before the first prod deploy, not after. Reflect this in REQ-002. Make pinning a release gate (no merge until Dockerfile contains resolved semver). Record version in a committed artifact (`mcp-m365/VERSION` or Dockerfile comment) so `git log` surfaces tool-surface changes.

- **LOW** Missing rate limiting on the MCP endpoint
  - Evidence: REQ-001/REQ-011 expose `http://mcp-m365:3000/mcp` on `default` and `caddy_net`. No per-user or per-IP rate limit is described at the sidecar or at LibreChat's outbound MCP call site. SEC-002 addresses SSRF allowlisting but not abuse-rate.
  - Risk: A prompt-injected agent (or a malicious user) can drive a high volume of Graph calls under the signed-in user's identity, triggering Graph throttling tenant-wide and producing a noisy denial-of-service window. Phase-1 read-only scopes do not prevent read storms.
  - Resolution: Add a PERF/SEC requirement: cap concurrent in-flight `Microsoft365` tool calls per user (e.g., 4) and per conversation (e.g., 8) at the LibreChat MCP layer, and document the Graph 429 handling expectation alongside REQ-016.

#### Performance Findings

- **HIGH** Tail latency not budgeted; p95/p99 absent for tool-call latency
  - Evidence: PERF-002 states: "Steady-state per-tool latency is dominated by Graph round-trip (typically <800 ms for a `/me/messages` listing); the MCP hop adds <50 ms on the same Docker network." No p95/p99 targets. PERF-001 similarly gives a single "5 seconds" cold-start figure with no percentile.
  - Risk: "Typically <800 ms" is a median (or hand-wave). Graph API tail latency for `/me/messages`, `/me/messageRules`, and especially `/search/query` routinely reaches multi-second p95 under throttling (Graph API has per-app and per-mailbox throttling limits). An agent that fans out across mail + calendar + files in one turn will see worst-case latency = sum of tail latencies, not sum of medians. With no p95/p99 SLO, on-call has no signal to distinguish "Graph is slow today" (expected) from "OBO exchange is degrading" (incident).
  - Resolution: Add explicit numeric targets to PERF-002: e.g., `p50 ≤ 1s, p95 ≤ 3s, p99 ≤ 8s for a single Graph-backed tool call end-to-end (LibreChat → MCP → Graph → MCP → LibreChat)`. State which spans are measured (OBO exchange, MCP hop, Graph round-trip). Reference the measurement plan (logs, traces, or a future observability hook — PRE-RESEARCH-013).

- **HIGH** Restart-only deploy causes synchronized OBO token-cache cold start (thundering herd on Entra) [also flagged by reliability as "Thundering herd on GraphTokenService cache after API restart" HIGH — same finding, two specialists]
  - Evidence: REQ-014: "Restarting the API (`./prod.sh restart api`) is the only LibreChat-side action needed after `librechat.yaml` changes." PERF-003: "`GraphTokenService` caches the per-user Graph token under `${user.openidId}:${scopes}` so consecutive tool calls within a single conversation reuse a single OBO exchange." The cache is in-process; `./prod.sh restart api` evicts it for every user simultaneously.
  - Risk: After every restart, the first M365 tool call per active user triggers a JWT-bearer OBO exchange to Entra (synchronous external call on hot path, no warm cache). For N concurrent users mid-conversation, this is N simultaneous round-trips to `login.microsoftonline.com`. Entra throttles per-app OBO requests; under burst, some users will see auth errors that look like REQ-015 missing-token errors but are actually transient throttling. Spec calls out no circuit breaker, no request coalescing (if two requests for the same user race, both will OBO-exchange), and no backoff strategy beyond MCP's connect-time circuit breaker.
  - Resolution: Add a non-functional requirement: bound concurrent OBO exchanges via single-flight (in-flight request coalescing keyed by `${user.openidId}:${scopes}` — additional callers wait on existing promise). Document expected post-restart OBO QPS and Entra throttling thresholds. Optionally pre-warm cache for active sessions on startup, or persist the OBO cache in Redis so restart preserves it. Specify error-classification: distinguish Entra throttle (retryable) from genuine missing-token (REQ-015). Verification: add a test that simulates concurrent first-tool-calls and asserts only one OBO exchange per user.

- **MEDIUM** Token cache key shape leak: changing `OPENID_GRAPH_SCOPES` orphans every cached token
  - Evidence: MODULE-003 Hides: "OBO scope-set cache-key implications inside `GraphTokenService` (cache key is `${user.openidId}:${scopes}`, so the scope string is part of the cache contract; changing it invalidates cached tokens)." REQ-009 mandates updating `OPENID_GRAPH_SCOPES`; future phase-2 scope additions (Mail.ReadWrite etc.) will re-key the cache.
  - Risk: (a) Anti-pattern "Token cache key shape leak": the cache key includes the full scope string, so any non-identical scope-set serialization (different order, whitespace, case) produces a cache miss. The spec does not specify normalization (sorting, lowercasing, trimming). (b) Every phase-2 scope expansion is a cache-wide invalidation event — the same thundering-herd profile as REQ-014 restart. (c) Per-user multi-conversation flows with subtly different scope subsets (e.g., a future per-tool scope-pinning feature) would produce N cache entries per user.
  - Resolution: Specify scope-key normalization: sort + lowercase + comma-join the scope list before hashing into the cache key. Document that scope changes are cache-invalidating and should be coordinated with the restart-OBO mitigation above. Optionally: cache the scope-set independent of presentation order using a deterministic hash.

- **MEDIUM** Cold-start budget (5s) is asserted, not measured; `initTimeout: 150000` is 30x the budget [overlaps with reliability "Weak start-ordering condition" HIGH on the readiness-vs-liveness conflation]
  - Evidence: PERF-001: "Cold-start latency for the first MCP call after `mcp-m365` restart is allowed up to 5 seconds (Softeria server + lazy tool registration). `initTimeout: 150000` ms is set to absorb this comfortably." REQ-018: `condition: service_started` + `initTimeout: 150000`.
  - Risk: Anti-pattern "Cold start tolerance unbounded": 150s is a retry/timeout budget 30× the stated 5s cold-start. If actual cold-start drifts upward (Softeria adds tools, image grows, alpine cold cache, network DNS), the gap means a degraded sidecar can hang LibreChat MCP init for 2.5 minutes before failing. During this 150s window, what happens to user tool calls that route to `Microsoft365`? Spec doesn't say — likely they queue or time out per `timeout: 45000`, but the interaction between API-container readiness and MCP init is unspecified. `service_started` only waits for the container to start, not for the MCP endpoint to bind.
  - Resolution: Tighten `initTimeout` to ~15000-30000 ms once measured cold-start is known (drop after OD-1 pin). Add a measurement requirement: log cold-start duration on every `MCPManager` connect; alert if it exceeds 80% of `initTimeout`. Clarify behavior of in-flight tool calls during the 150s window (rejected fast vs. queued). Consider a Docker healthcheck on `/mcp` (or fallback per OD-5) and `condition: service_healthy` instead of `service_started` to eliminate the race.

- **MEDIUM** Unbounded MCP tool surface: 70+ Softeria tools registered per connect, not per use
  - Evidence: REQ-012: "No `--discovery` flag is passed; LibreChat's event-driven lazy tool loading (v0.8.3+) governs which Softeria tools are surfaced to a given conversation." MODULE-001 Hides: "The 70+ Softeria Graph tool implementations…"
  - Risk: Anti-pattern "Unbounded MCP tool surface": LibreChat's "lazy tool loading" controls *surfacing to the model*, but the MCP server still *registers* all 70+ tools on every fresh streamable-http session (this is what `initTimeout` is absorbing). Each tool registration is JSON-schema serialization across the wire. For an agent enabled with `Microsoft365`, the per-conversation cost of fetching the tool list is paid even if only `Mail.Read` is ever used. The spec describes this as a non-issue but provides no measurement: how big is the tool-list response payload? How many tokens does the model see in its tool-list context?
  - Resolution: Measure and document: (a) size of the MCP tool-list response, (b) tool-list registration latency, (c) prompt-token cost of injecting 70+ tool schemas into the model context. If costs are high, recommend Softeria configuration to subset tools (or revisit `--discovery` if it now exists). Add to PERF section: expected steady-state tool count surfaced per conversation, and a budget.

- **LOW** Per-request token-cache TTL and refresh timing not specified
  - Evidence: PERF-003: "When a cached token expires or nears expiry, the service re-runs the JWT-bearer OBO exchange on the next call." MODULE-003 references `GraphTokenService` but doesn't pin TTL.
  - Risk: "Nears expiry" is unspecified. If the refresh trigger is too aggressive (e.g., 30 min before expiry), users pay extra OBO exchanges for no benefit. If too lax (e.g., 30 seconds before expiry), in-flight tool calls can fail mid-flight when the cached token expires between MCP-hop start and Graph reply. No reference to whether Graph token lifetime is 1h (typical) or shorter under conditional access.
  - Resolution: Specify the refresh trigger explicitly (e.g., "refresh when remaining TTL < 5 minutes"). Document Graph token nominal lifetime assumption (1h). Reference where `GraphTokenService` defines this so future readers can find it.

- **LOW** No measurement plan for any PERF requirement
  - Evidence: PERF-001/002/003 use bare numbers ("5 seconds", "<800 ms", "<50 ms") without stating how they're measured, where the data lives, or what triggers an alert.
  - Risk: Performance regressions cannot be detected without a baseline. The Verification Plan smoke tests confirm functional correctness only ("expect a `/me` response") and have no latency assertions.
  - Resolution: Add a "Performance Measurement" subsection to the Verification Plan: list which logs/metrics to scrape (existing LibreChat logs? new traces?), how to compute p50/p95/p99 from them, and what dashboard/alert would catch regression. Reference PRE-RESEARCH-013 if observability work is in the roadmap.

#### API Contract Findings

- **HIGH** Tool-call contract drift via unpinned Softeria image [merged-severity HIGH; security listed this same root cause as LOW]
  - Evidence: REQ-002 ("installs `@softeria/ms-365-mcp-server` (pinned to a specific version after first successful deploy)"), OD-1 ("First deploy uses `@latest`; immediately after green smoke-test, pin to the resolved version"), implementation step 1 (`Dockerfile` uses `@latest`).
  - Risk: The first deploy ships with a floating `@latest` tag — every `./prod.sh build mcp-m365` between initial deploy and the deferred pin step can silently change the tool list, tool input/output schemas, and `--toon` normalization behavior. Agents that learned to call `messages-list` may discover it renamed or its arguments restructured on a rebuild. Worse, OD-1 is a soft commitment with no enforcement; if the operator forgets the pin step the contract stays unpinned indefinitely. The `Microsoft365` MCP entry has no `version` or schema-hash check on LibreChat's side, so drift is invisible until a tool call fails mid-conversation.
  - Resolution: Make REQ-002 require a concrete version pin from the very first build (resolve Softeria's current stable version during spec finalization and write it into the Dockerfile literal). Promote OD-1 from "deferred to first deploy" to a release gate: no merge of the implementation PR until the Dockerfile contains a resolved semver. Add a verification-plan step that records the exact resolved version in a committed `mcp-m365/VERSION` or similar artifact, so a future `git log` shows when the tool surface changed.

- **HIGH** Bearer token contract underspecified at the LibreChat-to-sidecar boundary
  - Evidence: REQ-004 (`headers.Authorization: "Bearer {{LIBRECHAT_GRAPH_ACCESS_TOKEN}}"`), REQ-007 ("placeholder is resolved by `resolveGraphTokenPlaceholder()` via `GraphTokenService.getGraphApiToken()`"), MODULE-001 Public Interface ("consumes `Authorization: Bearer <graph-token>` per request"), MODULE-002 Public Interface ("Implicit: the `{{LIBRECHAT_GRAPH_ACCESS_TOKEN}}` placeholder contract").
  - Risk: The spec describes the wire format (`Authorization: Bearer <jwt>`) but never specifies what Softeria's server is contractually required to accept. There is no statement about (a) which audience the JWT must target (`https://graph.microsoft.com` vs `api://<client-id>` vs `00000003-0000-0000-c000-000000000000`), (b) what the sidecar does on a malformed/expired/wrong-audience token — does it 401 cleanly, or does Graph 401 surface back through MCP framing? (c) whether the resolver injects an empty string when no Entra session exists (REQ-015 hints at this for local-auth users but doesn't define the wire shape). Without this nailed down, a future Softeria release could change its token validation (e.g., start requiring `aud=api://...`) and silently break every M365 call, or an empty placeholder could ship `Authorization: Bearer ` to the sidecar with undefined behavior.
  - Resolution: Add a REQ between 007 and 008 ("Bearer token contract") stating: (1) the token is a Graph access token with audience `https://graph.microsoft.com` obtained via OBO from the user's OIDC session; (2) the sidecar must treat it as opaque — no local signature validation, only Graph upstream; (3) when `GraphTokenService.getGraphApiToken()` returns null (non-Entra session), the `Authorization` header is omitted entirely, not sent with an empty Bearer; (4) Graph 401 from upstream surfaces as an MCP tool error with a stable error code. Cross-reference this requirement from REQ-015 and REQ-016.

- **MEDIUM** MCP protocol version not pinned
  - Evidence: REQ-004 (`type: streamable-http`), RESEARCH-005 ("Deprecated in MCP spec March 2025, still supported" re SSE; streamable-http "Recommended for new deployments"), no protocol-version field anywhere in the `Microsoft365` entry.
  - Risk: MCP is an evolving protocol (RESEARCH-005 explicitly notes the SSE deprecation in March 2025 and the streamable-http migration). A Softeria release could adopt a newer MCP protocol revision that LibreChat's `MCPManager` does not yet implement — or vice versa. The spec gives no compatibility matrix and no protocol-version handshake check. If MCP introduces a breaking change to streamable-http framing in 2026, both sides will simply fail to negotiate, and the failure mode (per circuit-breaker rules cited in RESEARCH-005: 7 cycles, 45s window) is a long blocked startup, not a clear diagnostic.
  - Resolution: Add an OD or REQ that records the targeted MCP protocol version (e.g., "MCP 2025-06" or whatever rev LibreChat's `MCPManager` implements at spec time), and require the smoke test to log Softeria's reported protocol version. If the sidecar advertises a version newer than what `MCPManager` supports, fail the connect with a logged warning instead of relying on circuit-breaker retries.

- **MEDIUM** Ambiguous error shape for Graph 403 surfacing
  - Evidence: REQ-015 ("clear error to the agent describing the missing token, not a 500"), REQ-016 ("Graph 403 must surface to the agent as a clean tool error, not as a server crash or stuck stream"), Verification Plan negative tests (Missing consent → "403 surfaced as a tool error"; Phase-1 write attempt → "Graph 403, captured cleanly").
  - Risk: Three different requirements (REQ-015, REQ-016, the "Phase-1 write attempt" negative test) all gesture at "tool error" but none defines the wire shape. Is it MCP `{ "isError": true, "content": [...] }`? A thrown exception serialized by `MCPManager`? A specific error code (`InsufficientScope`, `Unauthorized`)? Without a defined shape, the LLM cannot reliably distinguish "you don't have permission for OneDrive" from "the sidecar is down" — both look like a generic tool failure. SPEC-009 PII detection (REQ-019) also flows over this path and needs a stable error shape to avoid attempting redaction on error bodies.
  - Resolution: Define a single error response schema for the three failure modes (no token / missing scope / write attempt) in a new sub-section under Success Criteria. Specify: HTTP status returned by sidecar (or MCP error code in the tool-call response), the error-body JSON shape, the message field convention, and whether Graph's `code` (`Authorization_RequestDenied`, `ErrorAccessDenied`) is preserved verbatim or remapped. Make REQ-015, REQ-016, and the negative tests reference this schema by name.

- **MEDIUM** `serverInstructions` is a prompt-time contract with no drift control
  - Evidence: REQ-004 (`serverInstructions` "names every M365 surface available to the agent"), UX-002 ("`serverInstructions` string … names the M365 surfaces in human terms; the LLM sees this when choosing whether to invoke a tool"), Implementation step 3 (full text inlined), REQ-010 (no `--org-mode`, no Teams write tools).
  - Risk: `serverInstructions` is effectively a contract between the spec author and the LLM at every conversation. The inlined text lists "Outlook mail, Calendar, OneDrive, SharePoint, Excel, OneNote, To Do, Planner, Contacts, and Graph search" and asserts "All scopes are read-only in phase 1". When phase 2 lands (write scopes, `--org-mode` per OD-4) or when Softeria adds/removes a tool family, this text must be updated in lockstep — but the spec has no mechanism tying the `serverInstructions` text to either the actual tool list returned by the sidecar at init time or the scope set in REQ-008. A future scope expansion that forgets to update `serverInstructions` will leave the model believing it's still read-only while it can actually issue writes, or vice versa (model refuses operations it could perform).
  - Resolution: Either (a) add a verification-plan step that diffs `serverInstructions` content against `REQ-008` scopes and `REQ-010` flag set on every PR that touches `librechat.yaml`, or (b) generate `serverInstructions` text from a single source of truth (a constant) that also drives the scope list. Minimally, add a REQ stating "`serverInstructions` must be updated in the same PR as any scope change in REQ-008 or any `--org-mode`/feature-flag change in REQ-010."

- **LOW** Tool naming collision risk under `Microsoft365` group label
  - Evidence: UX-001 ("M365 tools appear under a group label of `Microsoft365` (matching the YAML key)"), RESEARCH-005 ("Softeria … 70+ tools" spanning Mail/Calendar/OneDrive/SharePoint/Excel/OneNote/ToDo/Planner/Contacts/Graph search), no enumeration of how Softeria names individual tools.
  - Risk: With 70+ tools surfaced under a single group label, name collisions become possible (e.g., a future MCP server also exposes a `search` or `list` tool). LibreChat's agent builder appears to use the YAML key as a namespace, but the spec does not state whether tool names are flat (`search`) or namespaced (`Microsoft365__search`). If flat, a future `mcpServers.Slack.search` would conflict. The spec also offers no allowlist/denylist for which of the 70 tools should be exposed in phase 1 — the agent builder will surface all of them, including ones (e.g., Excel charts, OneNote sections) that may not be in the intended phase-1 surface area despite being read-only.
  - Resolution: Add a clarifying note to UX-001 specifying tool namespacing convention (likely `Microsoft365_<tool>` or whatever `MCPManager` does today — confirm against existing `docs.mcp.cloudflare.com` integration). Consider adding an OD or REQ defining whether phase 1 ships with all 70+ Softeria tools or a curated subset (perhaps via a Softeria `--tools` filter flag if available).

- **LOW** `mcpSettings.allowedDomains` entry is a bare hostname (low-grade contract weakness) [merged with security MEDIUM finding above — kept here for visibility, counted once]
  - Evidence: REQ-005 ("bare-hostname entry `mcp-m365`"), OD-2 resolution ("`isDomainAllowedCore` matches hostname-only allowlist entries"), Implementation step 3.
  - Risk: Allowing a bare hostname (no scheme, no port) means any sibling container that responds on a port named `mcp-m365` would match — and inside `caddy_net` and `default` networks this is unlikely but not impossible if Compose service names ever collide with a future deployment. There is no protocol pin (anyone could swap the entry from `http://mcp-m365:3000/mcp` to `https://mcp-m365:443/...` without an allowlist update). For an internal allowlist this is a low-grade contract weakness, not a security hole, but it is a stricter-than-necessary allowlist semantics that the spec inherited from existing code rather than designed deliberately.
  - Resolution: Note in REQ-005 that the choice of bare hostname (vs `http://mcp-m365:3000`) is a consequence of existing `isDomainAllowedCore` semantics, not a spec preference. If `extractMCPServerDomain` ever changes to require origin matching, the allowlist entry must be updated — flag this dependency.

#### Module Depth Findings

- **MEDIUM** MODULE-002 risk tier understates "low" given it's the gate between delegated Graph data and the PII-detection wrapper
  - Evidence: SPEC-014 lines 138-154 — MODULE-002 `Risk` field marked `low`; `Hides` enumerates "PII-detection pass that wraps tool output (SPEC-009 reuse, REQ-019)" and "async preprocessing pipeline that swaps the placeholder for a freshly minted Graph token before each connect".

These are not "pure config"; they are the integration seams where a mis-wired header, a wrong `serverInstructions`, or a regressed placeholder resolution silently leaks Graph data into agent output before PII can catch it. Marking the only module that owns REQ-019 (PII pass) and SEC-002 (SSRF surface) as `low` distorts review depth allocation downstream and contradicts the "risk-tier-driven review depth" convention used elsewhere in this repo's specs.
  - Resolution: Raise MODULE-002 `Risk` to `medium`. Add one sentence in the Risk paragraph: "Although the module is config-shaped, it owns the only path that turns delegated Graph data into agent tool output (REQ-019) and the only enforcement of the new MCP target hostname (SEC-002); a silent regression here bypasses every downstream guard."

- **LOW** MODULE-002 `Hides` includes infrastructure it does not own
  - Evidence: SPEC-014 lines 146-148 — MODULE-002 `Hides` lists `MCPManager` streamable-http connector, circuit-breaker, the `processMCPEnv` pipeline, and `isMCPDomainAllowed` enforcement.
  - Risk: Structural — these are pre-existing LibreChat subsystems, not complexity this module hides. Listing them inflates the apparent depth and blurs the boundary: a future reader cannot tell which of these the spec is changing versus reusing. This is a mild form of "wide interface, thin internals" inverted — the `Hides` field is being used to claim depth via inherited infrastructure rather than by hiding new complexity. The module's actual hidden complexity is narrower: the placeholder-to-Bearer-header binding plus the hostname-allowlist semantics for an internal Docker DNS name.
  - Resolution: Reframe MODULE-002 `Hides` to distinguish "reused (depended-on)" from "newly hidden." Newly hidden: the binding of `{{LIBRECHAT_GRAPH_ACCESS_TOKEN}}` to the `Microsoft365` header, the bare-hostname allowlist semantic for `mcp-m365` (OD-2 resolution), and the surfacing of the `Microsoft365` tool group plus `serverInstructions` into the agent builder. Move `MCPManager` circuit-breaker, `processMCPEnv`, and `isMCPDomainAllowed` into a "Depends on (unchanged)" sub-bullet.

- **LOW** REQ-017 handled as cross-module non-goal is defensible but flag for visibility
  - Evidence: SPEC-014 line 172 — "Note on REQ-017" placed after MODULE-003; explicitly states REQ-017 is intentionally not owned by any module.
  - Risk: Structural — anti-pattern #9 (missing spec refs) would normally flag this. However, the spec's handling is the correct pattern: REQ-017 is a bounding constraint ("the picker is untouched"), not an action item. Demoting it to a non-goal in the "Out of Scope" section would be cleaner, but the current "Note" treatment is acceptable. Flagging LOW only because a future reader scanning module Spec refs may briefly perceive REQ-017 as orphaned before reading the note.
  - Resolution: Optional — either keep current treatment, or move REQ-017's substantive text into "Out of Scope (Explicit Non-Goals)" and leave a single back-reference in Functional Requirements. No structural change required.

#### Privacy Findings

- **HIGH** Sub-processor disclosure for Softeria image is absent (GDPR Art. 28) [overlaps with security HIGH "Confused-deputy" and api-contract HIGH "Tool-call contract drift" on shared supply-chain root cause]
  - Evidence: REQ-002 ("installs `@softeria/ms-365-mcp-server`"); MODULE-001 risk note ("only LibreChat-adjacent process touching every user's Graph data"). Spec never names Softeria as a sub-processor of M365 personal data.
  - Risk: Under GDPR Art. 28(2) & (4), the controller (Memodo or its customer) must authorise and disclose sub-processors. Softeria's published code processes every user's mail, calendar, contacts, files in flight. Although the container is operated by Memodo, the *software supplier* relationship still imports a software-supply-chain disclosure obligation, and any future shift to Softeria-hosted endpoints would silently widen the data path. Absence of a sub-processor / vendor record breaks Art. 30 records-of-processing-activities and DPA transparency to customers.
  - Resolution: Add a "Sub-processor & supplier disclosure" subsection under Non-Functional Requirements (or a new SEC-006) stating: (a) Softeria is a software supplier, not a hosted sub-processor in phase 1; (b) the image is self-hosted on Memodo infrastructure and processes user-scoped Graph tokens transiently; (c) the package source (npm `@softeria/ms-365-mcp-server`) and pinned version are recorded in the RoPA / vendor inventory; (d) any future move to a Softeria-hosted SaaS endpoint requires a new spec and DPA amendment.

- **HIGH** Joint-controller / processor role for ingested M365 content is undefined
  - Evidence: Executive Summary frames MemodoAI as the deployment operator; SEC-004 says "LibreChat conversation logs + Graph activity logs together produce a per-user trail"; no statement of controller/processor role for the M365 data that flows into LibreChat conversations.
  - Risk: Once a user pulls a colleague's calendar invite (containing attendee names/emails) or a SharePoint document (containing third-party PII) into a LibreChat conversation, that personal data is no longer governed solely by Microsoft's controller relationship — LibreChat persists it in conversation logs, the embedding store, and audit trails. Without a written role determination (Memodo as controller for its own employees' usage logs; processor for customer-tenant data), DPAs, breach-notification timelines, and DSR routing are ambiguous. This is also Art. 26 territory if customers are co-controllers.
  - Resolution: Add an "Information governance" subsection (or extend Executive Summary) defining (a) Memodo's role for the LibreChat-side persistence of M365-derived content, (b) the customer's role for the underlying Graph data, (c) how a deletion or access request that targets *ingested* M365 content is honoured. Link to the Memodo DPA section that covers this. If undecided, list as a blocking open decision (OD-6), not silence.

- **HIGH** Retention policy for tool output ingested into conversations is unspecified
  - Evidence: REQ-019 ("tool output... traverses the same agent message path as any other tool result"); no retention requirement is stated. Out-of-scope list does not address it.
  - Risk: Mail bodies, calendar attendees, SharePoint document text, and contact phone numbers will end up in MongoDB conversation logs and (downstream) any embedding/vector store. Default LibreChat retention is "until user deletes the conversation" — i.e., indefinite. GDPR Art. 5(1)(e) requires storage limitation; SPEC-009 (PII) is about redaction at boundary, not retention. Indefinite retention of third-party PII (attendees, recipients) ingested by one user is a clear over-retention pattern.
  - Resolution: Add REQ-020 (or a Retention subsection) stating: (a) M365 tool output inherits conversation-level retention, (b) named default retention period (e.g., conversations >12 months purged unless pinned), (c) tool-output payloads are not separately cached outside the conversation record, (d) explicit pointer to where the retention timer is enforced (current code or follow-up ticket). Mark as a blocking dependency if not yet implemented in LibreChat.

- **HIGH** DSR (right-to-erasure / right-of-access) flow for ingested M365 data is undocumented
  - Evidence: Spec describes no path for "user X requests deletion / export of all M365-derived content from their LibreChat conversations." Out-of-scope list does not address DSR.
  - Risk: GDPR Art. 15 & 17. A user who requests erasure must have ingested M365 data deleted from LibreChat conversation logs, agent memories, and any downstream stores (e.g., embedding index used by SPEC-008 admin reporting). A user requesting access must receive that data in portable form. Without a documented flow, support staff will either over-delete (operational risk) or under-delete (regulatory risk).
  - Resolution: Add a "Data-subject rights" subsection naming: (a) which existing LibreChat DSR mechanism covers ingested tool output (and whether one exists), (b) confirmation that tool output is not stored outside the conversation document, (c) handoff to whichever spec/runbook owns DSR fulfilment, (d) explicit flag that admin-reporting dashboard (SPEC-008) aggregates may need re-aggregation post-erasure. If LibreChat lacks a DSR runbook today, mark this as a cross-cutting prerequisite (blocking for production rollout under GDPR).

- **MEDIUM** No consent UX for new personal-data categories (Art. 13/14 transparency)
  - Resolution context: Out of Scope explicitly defers "Custom UI for per-user M365 consent management — relies on the standard Entra consent prompt at sign-in."
  - Risk: The Entra consent prompt lists Graph scopes in technical language (e.g., `Files.Read.All`). The user is consenting to the *agent* reading these on the user's behalf at agent-tool-call time — a different, broader consent than "let LibreChat read my mail." Calendar and contact scopes also pull in *third-party* PII (attendees, contacts) for whom the user has no consenting authority. GDPR Art. 13/14 transparency obligations are not satisfied by an Entra scopes screen alone. Phase-1 reliance on the default Entra prompt is acceptable only if Memodo's existing privacy notice already documents (a) what data the agent may read, (b) why (purpose), (c) retention, (d) third-party-PII implications.
  - Resolution: Add a UX requirement (UX-003) noting that the Memodo privacy notice and/or first-use modal must list the new data categories (mail bodies, calendar attendees, contact PII, SharePoint files) in plain language at the point an agent is first granted Microsoft365 tools — not buried in an Entra consent screen. Reference the privacy notice location explicitly. If reuse of Entra consent is deliberate, document that decision as an OD with an acceptance criterion (privacy notice updated).

- **MEDIUM** Sidecar log content is unspecified — payload-leak risk [merged with security MEDIUM "Bearer tokens in logs"; counted once]
  - Evidence: OPS-002 ("Logs to stdout/stderr. The sidecar's logs are accessible via `docker compose logs` without any volume mounts").
  - Risk: Softeria server log defaults are not characterised. If it logs request URLs (e.g., `/me/messages?$filter=subject eq '...'`) or response bodies, mail subjects, attendee emails, and file names become discoverable to anyone with `docker compose logs` access on the host — which is broader than the conversation log ACL. This is a classic "logs contain payloads" anti-pattern that the spec doesn't refute.
  - Resolution: Add to OPS-002 (or new OPS-004): "Sidecar log level is set to a verified non-payload-logging level; specifically, log lines must not include Graph URL query strings beyond path templates, response bodies, mail subjects, recipient addresses, file names, or attendee identifiers. The first-deploy smoke test (Verification Plan §1) must inspect a representative log sample to confirm." If Softeria's defaults are unsafe, pass a `--log-level=error` (or equivalent) flag in REQ-002.

- **MEDIUM** Audit-reconstruction claim risks logging request/response bodies [merged with security MEDIUM "SEC-004 audit-reconstruction"; counted once]
  - Evidence: SEC-004 ("LibreChat conversation logs + Graph activity logs together produce a per-user trail").
  - Risk: "Conversation logs" in LibreChat already include the assistant turn that quotes tool output. If SEC-004 is interpreted as "the conversation log *is* the audit", then the per-user audit is by definition the personal data. That conflates audit-trail purpose (legitimate-interest / legal-obligation lawful basis) with conversation-history purpose (user's own data). It also creates a retention conflict: audit logs typically have a fixed retention window distinct from conversation retention, but here they're the same artifact.
  - Resolution: Refine SEC-004 to specify *what minimal metadata* constitutes the audit record (timestamp, user.openidId, tool name, scope, Graph endpoint path template, HTTP status code — explicitly excluding request body, response body, query-string filters, and recipient identifiers). State that Graph-side activity logs are the authoritative payload-aware record, retained by Microsoft, and reconstruction is `LibreChat metadata` ⋈ `Graph activity log` keyed by Entra user. This separates audit-purpose data from conversation-purpose data.

- **MEDIUM** No data-minimization requirement at the tool layer
  - Evidence: REQ-002 entrypoint `--http 3000 --toon`; REQ-019 treats *all* tool output as PII-detected. Softeria tools by default return the full Graph object shape (e.g., a message returns body, recipients, attachments-meta, internetMessageHeaders).
  - Risk: GDPR Art. 5(1)(c) data minimization. Returning a full Graph `message` for a "summarise my last 5 mails" intent leaks more PII into the conversation log than the user asked for. SPEC-009 PII detection can redact regex-detectable PII (emails, phone numbers) but not "this is the senior counsel's full draft contract body that the user only wanted a one-line summary of." Minimization should happen at the tool boundary.
  - Resolution: Add REQ-021 (Data minimization at tool boundary) requiring that Microsoft365 tool wrappers apply `$select` / projection where Graph supports it, and that the `serverInstructions` field directs the model to request only needed fields. If Softeria does not support field projection on its tool shapes, document this as a known limitation and offset with stricter retention.

- **LOW** Cross-border transfer story relies on assumption, not configuration
  - Evidence: SEC-005 ("EU data residency preserved. No traffic exits the Memodo Entra tenant's region. The MCP sidecar makes outbound TLS to `graph.microsoft.com` only").
  - Risk: `graph.microsoft.com` is a global Microsoft-fronted endpoint; tenant-region pinning is a property of the tenant config and Microsoft's EU Data Boundary commitment, not of the TLS endpoint name. The spec asserts residency but does not state the lawful basis (EU Data Boundary contractual commitment with Microsoft, plus tenant region = EU). For a privacy reviewer, this is an *assertion without evidence*.
  - Resolution: Refine SEC-005 to name the lawful-residency mechanism explicitly: "Microsoft EU Data Boundary contractual commitment applied to the Memodo Entra tenant (region: EU). No additional cross-border transfer is introduced by this spec; npm install of `@softeria/ms-365-mcp-server` at image-build time occurs on EU-based Hetzner hosts and pulls public package metadata from the npm registry (no personal data in transit)." This closes the build-time-vs-runtime gap and names the legal hook.

- **LOW** Build-time supply-chain — npm install at deploy time on prod host [merged with security LOW / api-contract HIGH on supply chain; counted once under api-contract HIGH]
  - Evidence: REQ-002 (Dockerfile `npm install -g @softeria/ms-365-mcp-server`); REQ-013 ("Image build via repo path... sidecar builds from a path inside this repo... a `./prod.sh build mcp-m365` rebuilds it from the prod host's local working tree").
  - Risk: Not a privacy *runtime* concern (no personal data in flight at build), but `@latest` plus build-on-prod-host means a typosquat or supply-chain compromise to Softeria's npm namespace would land on the prod host that handles every user's Graph data. Adjacent to privacy because the trust boundary for "who processes M365 PII" expands to "whoever can publish under `@softeria/`".
  - Resolution: Tighten OD-1 to require pinning to a specific version *and* recording the resolved tarball SHA-256 (`npm install @softeria/ms-365-mcp-server@<version>` then `npm view ... dist.integrity`) in `mcp-m365/Dockerfile` as a comment. Phase-2 image-registry publication (already listed in Future Work) removes the prod-host build-time fetch.

#### Reliability Findings

- **HIGH** Weak start-ordering condition without readiness gate (anti-pattern: missing health-check semantics distinction + no explicit failure-mode behavior)
  - Evidence: REQ-018 — "`api` service declares `depends_on: [mcp-m365]` with `condition: service_started` ... Combined with `startup: true` on the `Microsoft365` MCP entry, this guarantees the sidecar is at least up-and-listening before LibreChat attempts its initial connect; `initTimeout: 150000` then absorbs cold-start tool registration." OD-5 — "Verify on first build whether the Softeria server exposes `GET /health` ... smoke test must fall back to probing `GET /mcp` and accepting any non-5xx response as proof-of-life."
  - Risk: `service_started` is Compose's weakest condition — process spawned, but port may not yet bind and MCP handshake may not be ready. Liveness (`/mcp` non-5xx) and readiness (all 70+ Softeria tools registered) are conflated. LibreChat's initial connect inside the 150s window may succeed on handshake but the tool registry could be partial, causing tool calls to "disappear" or fail for the first conversation after restart. Spec gives no behavior contract for "port open but registry empty" — agents see a tool missing, not a deferred retry.
  - Resolution: (1) Replace `service_started` with `service_healthy` and require Softeria sidecar to expose a real `/ready` (or `/health`) endpoint that returns 200 only after lazy tool registration is initialized. (2) Resolve OD-5 BEFORE first deploy, not after — make it a precondition. (3) Add a spec clause: "If `/mcp` responds before tool registry is populated, LibreChat must retry tool discovery up to N times within `initTimeout`."

- **HIGH** Thundering herd on GraphTokenService cache after API restart [merged with performance HIGH "Restart-only deploy causes synchronized OBO cold start"; same root cause, counted once]
  - Evidence: REQ-014 — "Adding or changing the sidecar requires no LibreChat API container rebuild. Restarting the API (`./prod.sh restart api`) is the only LibreChat-side action needed". PERF-003 — "`GraphTokenService` caches the per-user Graph token under `${user.openidId}:${scopes}` so consecutive tool calls within a single conversation reuse a single OBO exchange." Verification step 5 — "expect one OBO exchange per (user, scope-set) per cache TTL".
  - Risk: API restart wipes the in-memory token cache. N concurrent active users hitting M365 tools in the seconds after restart all trigger simultaneous OBO exchanges against Entra. Entra throttling under burst load (HTTP 429) cascades into stuck tool calls. No spec acknowledgement of cache-stampede protection (e.g., single-flight, request coalescing, jittered backoff). At scale this becomes a self-DOS on the OBO endpoint after every deploy.
  - Resolution: Add a non-functional requirement: "Concurrent OBO exchange requests for the same `${user.openidId}:${scopes}` cache key MUST be coalesced into a single in-flight call (single-flight pattern). On cache miss, additional callers wait on the existing in-flight promise rather than issuing parallel OBO requests." Verify in test plan — currently absent.

- **HIGH** Sidecar single point of failure with no spec'd failure-mode behavior for "hung but up"
  - Evidence: Rollback — "Sidecar unhealthy: `./prod.sh stop mcp-m365` — agents lose M365 tools but every other feature continues unaffected". Module-001 risk — "Risk is 'medium' rather than 'low' because this is the only LibreChat-adjacent process touching every user's Graph data". No retry/circuit-breaker spec'd for the sidecar itself.
  - Risk: `mcp-m365` is a single container instance with no replication. The rollback assumes the failure mode is "down" (clean) — but the more common SaaS sidecar failure is "up but unresponsive" (Node event loop blocked, memory pressure, GC pause, hung outbound TLS to graph.microsoft.com). In that state, every M365 tool call hangs until LibreChat's 45s `timeout` fires — repeatedly, for every active user. SSE streams may stall. No spec'd watchdog or restart trigger for unresponsive-but-up. The 45s timeout × 70 tools × N users compounds quickly into perceived total outage.
  - Resolution: Add (a) Docker `healthcheck` block to the sidecar service definition with explicit `interval`, `timeout`, `retries`, `start_period` — auto-restart on unhealthy. (b) A reliability requirement naming the existing MCP reconnect circuit breaker ("max 7 cycles, 45s window, exponential backoff" per RESEARCH-005 §Security) and confirming the spec relies on it; without naming it, the behavior is silently dependent on `@librechat/agents` defaults. (c) Resource limits (mem/cpu) on the sidecar so an OOM is a clean kill, not a swap-thrashing zombie.

- **MEDIUM** No spec'd test for the stuck-stream / hung-upstream failure path (anti-pattern: smoke-test absent for the failure path)
  - Evidence: REQ-016 — "the Graph 403 must surface to the agent as a clean tool error, not as a server crash or stuck stream." Verification negative tests cover missing consent, non-Entra session, write attempt ("no stuck SSE stream") — but only via Graph-returned 403. No test for: sidecar hung, sidecar OOM mid-stream, graph.microsoft.com timing out, sidecar returning partial response then closing the connection.
  - Risk: The most operationally-painful failures (hung upstream, half-closed stream, timeout-mid-tool-call) are exactly the ones not exercised in the verification plan. "No stuck stream" is asserted but never tested under the conditions that actually produce stuck streams.
  - Resolution: Add a negative test: "Simulate sidecar unresponsiveness with `docker pause mcp-m365` during an active tool call. Expect: LibreChat tool call fails within `timeout: 45000` ms, the SSE stream emits a clean error event and closes, the agent loop recovers, the next prompt works after `docker unpause`." Also add: a Graph-503 simulation (e.g., point sidecar at an invalid Graph URL transiently) to verify upstream-degradation behavior.

- **MEDIUM** Cascading timeout risk between LibreChat and Softeria sidecar
  - Evidence: REQ-004 — "`timeout: 45000`, `initTimeout: 150000`". PERF-002 — "Steady-state per-tool latency is dominated by Graph round-trip (typically <800 ms for a `/me/messages` listing); the MCP hop adds <50 ms". No spec'd inner Softeria→Graph timeout, no spec'd HTTP client timeout inside Softeria.
  - Risk: LibreChat's outer 45s timeout has no defined relationship to Softeria's internal Graph HTTP client timeout. If Softeria's default Graph timeout is ≥45s (likely — Node `fetch` has no default timeout), LibreChat cancels the outer call but Softeria continues holding the inbound HTTP connection and its outbound Graph request, leaking sockets and amplifying retry pressure. Classic cascading-timeout anti-pattern.
  - Resolution: Add a reliability requirement: "Softeria's outbound timeout to graph.microsoft.com MUST be configured to a value strictly less than LibreChat's `timeout: 45000` (recommend 30000 ms) so the inner call fails cleanly before the outer timeout fires." If Softeria does not expose this config, document it as a known constraint and consider a sidecar HTTP proxy that enforces the inner timeout.

- **MEDIUM** Long-tail dependency on graph.microsoft.com without SLO acknowledgement
  - Evidence: Solution Approach — "the server proxies to `graph.microsoft.com`". SEC-005 — "outbound TLS to `graph.microsoft.com` only". No mention of Graph's SLO, no mention of behavior during Graph regional degradation.
  - Risk: All M365 tools share a single external SaaS dependency. Graph degradation (Microsoft has had multi-hour regional outages) makes every M365 tool fail simultaneously. Spec doesn't acknowledge the upstream SLO mismatch or define expected behavior (fail-fast with intelligible "M365 temporarily unavailable" vs. timeout-and-retry-storm).
  - Resolution: Add a paragraph under Non-Functional Requirements: "REL-001: Upstream Graph degradation behavior. When graph.microsoft.com returns 5xx or times out, the failure surfaces to the agent as a tool error within `timeout` ms. LibreChat MUST NOT retry beyond the framework's built-in MCP reconnect circuit breaker (RESEARCH-005: max 7 cycles, 45s window, exponential backoff). Agents should receive a single, intelligible error rather than N retries × M users × K tools amplification."

- **MEDIUM** Implicit circuit-breaker dependency (anti-pattern: circuit-breaker implicit)
  - Evidence: RESEARCH-005 §Security — "Circuit breaker for reconnection (max 7 cycles, 45s window, exponential backoff)" cited as existing LibreChat MCP behavior. SPEC-014 does not name it anywhere.
  - Risk: Spec silently relies on framework-default behavior that may change across `@librechat/agents` versions. A future upgrade that tunes these defaults could regress production behavior with no spec'd guardrail. Hidden retry amplification (LibreChat reconnect + framework reconnect + agent retry + user retry) is unbounded by spec.
  - Resolution: Add a reliability requirement naming the circuit breaker explicitly: "REL-002: MCP reconnect circuit breaker. LibreChat's existing reconnect behavior (max 7 cycles, 45s window, exponential backoff) governs `Microsoft365` server reconnection. Changes to these defaults in `@librechat/agents` MUST be reviewed against this spec." This pins the contract.

- **LOW** Restart-cascade risk on full-stack redeploy
  - Evidence: Deploy sequence — "`./prod.sh build mcp-m365 && ./prod.sh up -d mcp-m365 && ./prod.sh restart api`". `depends_on` with `service_started` chains api → mcp-m365.
  - Risk: A full `./prod.sh restart` (not just api) restarts both api and mcp-m365. If both restart in close succession, the post-restart thundering-herd (per HIGH finding above) hits a not-yet-warm sidecar. Combined cold-start (sidecar 5s + OBO cache cold + tool registration) makes the first 10-15s after redeploy fragile.
  - Resolution: Document the recommended ordered restart in OPS section: "When restarting both services, restart `mcp-m365` first, wait for healthcheck pass, then restart `api`. Avoid `./prod.sh restart` without an explicit service name during business hours."

- **LOW** `/health` endpoint contract unverified before first deploy (anti-pattern: smoke-test absent for failure path)
  - Evidence: OD-5 — "Verify on first build whether the Softeria server exposes `GET /health`."
  - Risk: The smoke test's first step depends on a behavior the spec author has not verified. If `/health` is absent and the fallback (`/mcp` non-5xx) is also broken (e.g., Softeria requires a POST to `/mcp` and returns 405 on GET/HEAD), the smoke test has no proof-of-life signal and operators may believe the sidecar is healthy when it is not.
  - Resolution: Close OD-5 in the spec before merge: explicitly state which probe the smoke test uses and what the expected response is. Do not defer "verify on first build" — it's a reliability-critical contract.

## Cross-Specialist Observations

Six distinct cross-domain clusters emerged after dedup. These are where panel orthogonality paid off — they are the issues most likely to be missed by any single specialist reviewing in isolation.

1. **Supply-chain unpinned at first prod deploy (Security HIGH + API-Contract HIGH + Privacy HIGH + Privacy LOW)** — Four specialists hit OD-1 / REQ-002's `@latest` from four different angles: token replay if a malicious image lands (security), tool-contract drift if the schema changes mid-soak (api-contract), sub-processor disclosure failure under GDPR Art. 28 (privacy), and npm typosquat blast-radius (privacy LOW). Each angle alone is fixable; together they make pinning before first prod deploy a release gate, not a follow-up.

2. **Sidecar-as-token-custodian / sidecar-as-payload-leaker (Security MEDIUM + Privacy MEDIUM)** — The Verification Plan's smoke test §6 explicitly greps `Authorization: Bearer eyJ...` from `mcp-m365` logs. Security flags this as token-in-logs; privacy independently flags that Softeria's default log level may emit URL query strings, mail subjects, attendee emails, and file names. Merged resolution: define the sidecar log content contract (no auth headers, no bodies, no query-string filters, no recipient identifiers) and change the smoke test to assert *absence* rather than presence.

3. **Restart thundering herd on Entra OBO (Performance HIGH + Reliability HIGH)** — Two specialists independently flagged that REQ-014's "just restart api" combined with PERF-003's in-process token cache produces synchronized N-user OBO exchanges against `login.microsoftonline.com`. Resolution requires a single-flight (request coalescing) pattern keyed by `${user.openidId}:${scopes}` plus error-classification separating Entra 429 from genuine missing-token.

4. **Bearer token contract + scope contract + error-shape contract under-defined (Security MEDIUM + API-Contract HIGH + API-Contract MEDIUM)** — Three findings cluster: SEC-004 audit-reconstruction is hand-wavy, the Bearer audience/empty-string/null behavior is unspecified at the LibreChat-to-sidecar boundary, and the error shape for Graph 403 / missing-scope / write-attempt is referenced by three requirements with no defined schema. Resolution: one new sub-section under Success Criteria defining (token audience + null-handling + error-response JSON shape + correlation-ID propagation), referenced by REQ-007, REQ-015, REQ-016, SEC-004.

5. **`mcpSettings.allowedDomains` hostname-only weakness (Security MEDIUM + API-Contract LOW)** — Two specialists flagged that bare-hostname allowlist semantics inherited from existing `isDomainAllowedCore` are weaker than scheme+host+port. Resolution: either tighten to `http://mcp-m365:3000` (with a follow-up dependency if `isDomainAllowedCore` doesn't yet support port matching), or explicitly document the inherited weakness and constrain via REQ-002 to a single bound listener.

6. **Readiness vs. liveness conflation (Performance MEDIUM + Reliability HIGH + Reliability LOW)** — `service_started` + unverified `/health` + 150s `initTimeout` is flagged from three angles: cold-start budget asserted-not-measured (performance), readiness gate missing (reliability HIGH), `/health` contract unverified (reliability LOW). Merged resolution: resolve OD-5 before merge, switch to `service_healthy` with a Docker healthcheck that gates on tool-registry-ready (not just port-bound), and tighten `initTimeout` after measurement.

Additionally, the **module-depth MEDIUM** (MODULE-002 risk under-tiered as `low`) is cross-cutting in a different sense: it is the structural review that flags that the spec's own risk allocation directs downstream review attention away from the module that owns REQ-019 (PII passthrough) and SEC-002 (SSRF allowlist). Raising MODULE-002 to `medium` is a prerequisite for the security and privacy resolutions above to land in the right review depth on future PRs.
