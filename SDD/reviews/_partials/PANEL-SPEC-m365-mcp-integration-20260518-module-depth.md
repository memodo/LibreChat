#### Module Depth Findings

- **MEDIUM** MODULE-002 risk tier understates "low" given it's the gate between delegated Graph data and the PII-detection wrapper
  - Evidence: SPEC-014 lines 138-154 — MODULE-002 `Risk` field marked `low`; `Hides` enumerates "PII-detection pass that wraps tool output (SPEC-009 reuse, REQ-019)" and "async preprocessing pipeline that swaps the placeholder for a freshly minted Graph token before each connect".
  - Risk: Structural — the module's `Hides` list explicitly includes the PII-redaction handoff, the OBO preprocessing pipeline, and the `allowedDomains` enforcement path. These are not "pure config"; they are the integration seams where a mis-wired header, a wrong `serverInstructions`, or a regressed placeholder resolution silently leaks Graph data into agent output before PII can catch it. Marking the only module that owns REQ-019 (PII pass) and SEC-002 (SSRF surface) as `low` distorts review depth allocation downstream and contradicts the "risk-tier-driven review depth" convention used elsewhere in this repo's specs.
  - Resolution: Raise MODULE-002 `Risk` to `medium`. Add one sentence in the Risk paragraph: "Although the module is config-shaped, it owns the only path that turns delegated Graph data into agent tool output (REQ-019) and the only enforcement of the new MCP target hostname (SEC-002); a silent regression here bypasses every downstream guard."

- **LOW** MODULE-002 `Hides` includes infrastructure it does not own
  - Evidence: SPEC-014 lines 146-148 — MODULE-002 `Hides` lists `MCPManager` streamable-http connector, circuit-breaker, the `processMCPEnv` pipeline, and `isMCPDomainAllowed` enforcement.
  - Risk: Structural — these are pre-existing LibreChat subsystems, not complexity this module hides. Listing them inflates the apparent depth and blurs the boundary: a future reader cannot tell which of these the spec is changing versus reusing. This is a mild form of "wide interface, thin internals" inverted — the `Hides` field is being used to claim depth via inherited infrastructure rather than by hiding new complexity. The module's actual hidden complexity is narrower: the placeholder-to-Bearer-header binding plus the hostname-allowlist semantics for an internal Docker DNS name.
  - Resolution: Reframe MODULE-002 `Hides` to distinguish "reused (depended-on)" from "newly hidden." Newly hidden: the binding of `{{LIBRECHAT_GRAPH_ACCESS_TOKEN}}` to the `Microsoft365` header, the bare-hostname allowlist semantic for `mcp-m365` (OD-2 resolution), and the surfacing of the `Microsoft365` tool group plus `serverInstructions` into the agent builder. Move `MCPManager` circuit-breaker, `processMCPEnv`, and `isMCPDomainAllowed` into a "Depends on (unchanged)" sub-bullet.

- **LOW** REQ-017 handled as cross-module non-goal is defensible but flag for visibility
  - Evidence: SPEC-014 line 172 — "Note on REQ-017" placed after MODULE-003; explicitly states REQ-017 is intentionally not owned by any module.
  - Risk: Structural — anti-pattern #9 (missing spec refs) would normally flag this. However, the spec's handling is the correct pattern: REQ-017 is a bounding constraint ("the picker is untouched"), not an action item. Demoting it to a non-goal in the "Out of Scope" section would be cleaner, but the current "Note" treatment is acceptable. Flagging LOW only because a future reader scanning module Spec refs may briefly perceive REQ-017 as orphaned before reading the note.
  - Resolution: Optional — either keep current treatment, or move REQ-017's substantive text into "Out of Scope (Explicit Non-Goals)" and leave a single back-reference in Functional Requirements. No structural change required.
