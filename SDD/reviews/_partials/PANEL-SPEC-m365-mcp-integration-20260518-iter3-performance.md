#### Performance Findings (Iter 3)

- **H** Queue-wait timeout + Graph inner timeout SUM exceeds outer MCP timeout (cascading-timeout discipline violated)
  - Evidence: REQ-024 sets queue-wait timeout at 30000 ms; REQ-025 sets Softeria's inner Graph HTTP timeout at "target: 30000 ms"; REQ-004 sets outer MCP `timeout: 45000`. A call dequeued at queue-wait≈29s and then performing a Graph round-trip taking ≈30s totals ≈59s end-to-end — 14s past the 45s outer MCP timeout. REQ-024's stated guarantee ("emit `Throttled` BEFORE the outer MCP timeout fires") only holds for calls that time out *in the queue*; calls that just barely escape the queue and then hit a slow Graph response will surface as `UpstreamUnavailable` (outer-timeout class) rather than the correct class, exactly the failure mode REQ-024 says it prevents.
  - Risk: Tail-latency error-class confusion under load — agents see `UpstreamUnavailable` (suggesting retry/backoff) when the true cause is internal saturation (suggesting Throttled + `retryAfter`). REL-002's circuit breaker keys off `UpstreamUnavailable`, so misclassification could trip the breaker on what is really a self-inflicted throttle. Also: outer-timeout-fired calls leak the inner Graph socket past 45s — REQ-025's whole point was to prevent that.
  - Resolution: Make the budgets additive: either (a) queue-wait ≤ (outer MCP timeout − inner Graph timeout − MCP hop budget) = 45000 − 30000 − ~500 = ~14500 ms, OR (b) raise outer MCP timeout to ≥ (queue-wait + inner-Graph + MCP-hop) ≥ 62000 ms, OR (c) reduce queue-wait to ≤14000 ms. Add an explicit invariant to REQ-025: `queue_wait_max + graph_inner_timeout + mcp_hop_budget < outer_mcp_timeout`. Bake the inequality into a unit test alongside the REL-002 7-cycle/45s pin.

- **M** REQ-021 single-flight does not specify retry/backoff scope for transient 429 — re-stampede risk
  - Evidence: REQ-021: "Error classification: distinguish Entra HTTP 429 (retryable with backoff and jitter) from a genuine missing-token / consent-denied failure." OD-7 specifies the `Map<cacheKey, Promise<TokenResponse>>` populated before `await`, cleared in `finally`. The spec does not say WHERE backoff lives. If the in-flight promise rejects on 429 and every concurrent caller awaiting it sees the rejection, each caller then independently retries — producing a fresh K-caller stampede that single-flight just prevented. The `finally`-clear semantic guarantees the next caller after a 429 retries from a cold slot, so failure-mode stampedes are not bounded.
  - Risk: Thundering herd reappears on Entra-side throttling (worst at API restart, scope rotation, or Entra incidents). Defeats PERF-003's "one OBO exchange per (user, scope-set) per cache TTL" property exactly when Entra is least healthy.
  - Resolution: Specify that backoff lives INSIDE the single-flight call — the in-flight promise itself retries with jittered backoff (e.g., up to 3 attempts, base 200ms, full jitter) before rejecting. Concurrent callers ride out the retry as a single coalesced operation. Add a unit test: with the upstream stubbed to return 429 twice then 200, K=10 concurrent callers observe exactly ONE successful resolve and (≤3) Entra calls total, not (≤3 × K).

- **M** PERF-003 token-refresh threshold (<5min remaining) collides with REQ-024 max queue-wait
  - Evidence: PERF-003 refreshes at "remaining TTL less than 5 minutes (not on expiry, to avoid in-flight failures between cache check and Graph round-trip)." Token is read from cache at request entry (LibreChat → MCP). REQ-024 allows a queue-wait of up to 30s plus a Graph round-trip of up to 30s. A call entering at TTL=5min01s passes the refresh check, sits in the queue for 30s, then incurs a 30s Graph round-trip — token expires mid-Graph-call. Surfaces as Graph 401, not retried within the request lifecycle.
  - Risk: Sporadic, hard-to-reproduce 401s on long-tail queued calls; user sees `Unauthenticated` for what is really a budgeting bug. Not catastrophic (read-only, idempotent retry by user works), but pollutes the error-class distribution and confuses on-call.
  - Resolution: Raise the refresh threshold to ≥ (queue-wait-max + graph-inner-timeout + safety) = 30 + 30 + 30 = ~90s minimum, or restructure so the token is re-checked (and refreshed if needed) at the moment of header emission — i.e., AFTER dequeue, not at request entry. Document the chosen point in PERF-003.

- **M** No cache layer for read-heavy Graph responses; every tool call is a fresh round-trip
  - Evidence: PERF-002 budgets p50≤1s / p95≤3s / p99≤8s for end-to-end tool calls, but the only cache layer in the spec is the OBO token cache (PERF-003). Sidecar is stateless (REQ-003). No request coalescing on tool-result level. A read-heavy phase-1 surface (Mail, Files, Sites, Contacts) repeatedly invoked within a single conversation (e.g., agent paginating or refining a search) re-hits Graph on every call, paying the full p95.
  - Risk: Tail latency dominated by Graph round-trip; PERF-002 p95≤3s budget will fail to hold under realistic agent workflows (refine-and-retry loops) where the same underlying entity is fetched 3-5x per conversation turn. Misses a clear optimization for read-heavy operations.
  - Resolution: Either (a) explicitly call out "no Graph-result cache in phase 1; freshness preferred over latency; PERF-002 budgets measured on single-call basis, not amortized" — making the design choice explicit and bounding the budget interpretation, OR (b) add a short-lived (60-120s) per-(user, endpoint, params-hash) result cache in the OBO/MCP layer with a documented invalidation contract. Option (a) is acceptable for phase 1 if the budget is honest about it.

- **L** PERF-004 tool-list prompt-token cost is recurrent per conversation, not a one-time gate
  - Evidence: PERF-004 measures "(c) the prompt-token cost of injecting the resulting tool schemas into the model context per conversation. Targets to verify at first deploy: ... tool-schema prompt-token cost < 10K tokens." Gate is "On breach of any target: rollout is BLOCKED". Recurrence is not budgeted as ongoing cost — it's a one-time pre-rollout check.
  - Risk: With 70+ Softeria tools, a per-conversation 10K token preamble at scale (N conversations × M turns) is a recurring inference cost line item. If Softeria adds tools in a minor version bump (REQ-002 version bump), prompt-token cost can creep upward silently; only re-measured "on every Softeria version bump" per PERF-004, which is correct but not enforced as CI.
  - Resolution: Add a CI check (or a doc'd manual step) that diffs the tool-list payload size + tool-count on every PR that bumps `mcp-m365/VERSION`. Optionally express the prompt-token target as a per-conversation budget × expected-conversations-per-day to make the ongoing inference cost legible to product.

- **L** PERF-001 cold-start alert threshold (80% of `initTimeout: 150000` = 120s) is far above the stated target (5s) — too lax to be useful
  - Evidence: PERF-001: "an alert fires if duration exceeds 80% of `initTimeout`. `initTimeout: 150000` is the initial absorbing budget; it MUST be tightened to ≤30000 ms once measured cold-start is confirmed stable across 10 restarts." Until tightening, the alert fires only at 120s — 24x the 5s target. A cold-start regression from 5s to 60s (a real degradation) would not alert.
  - Risk: A meaningful cold-start regression sits undetected for the entire pre-tightening window (weeks 1-4 by PERF-001's manual measurement cadence). The alert is theatrical until `initTimeout` is tightened.
  - Resolution: Define the alert relative to the BASELINE in `mcp-m365/perf-baseline.json`, not `initTimeout`. E.g., "alert if cold-start p95 > 2× baseline p95 OR > 10s, whichever is lower." This is consistent with the "≥50% regression vs baseline blocks deploy" rule already in PERF-001 — apply the same standard to the runtime alert.
