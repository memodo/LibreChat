#### Performance Findings

- **HIGH** Tail latency not budgeted; p95/p99 absent for tool-call latency
  - Evidence: PERF-002 states: "Steady-state per-tool latency is dominated by Graph round-trip (typically <800 ms for a `/me/messages` listing); the MCP hop adds <50 ms on the same Docker network." No p95/p99 targets. PERF-001 similarly gives a single "5 seconds" cold-start figure with no percentile.
  - Risk: "Typically <800 ms" is a median (or hand-wave). Graph API tail latency for `/me/messages`, `/me/messageRules`, and especially `/search/query` routinely reaches multi-second p95 under throttling (Graph API has per-app and per-mailbox throttling limits). An agent that fans out across mail + calendar + files in one turn will see worst-case latency = sum of tail latencies, not sum of medians. With no p95/p99 SLO, on-call has no signal to distinguish "Graph is slow today" (expected) from "OBO exchange is degrading" (incident).
  - Resolution: Add explicit numeric targets to PERF-002: e.g., `p50 ≤ 1s, p95 ≤ 3s, p99 ≤ 8s for a single Graph-backed tool call end-to-end (LibreChat → MCP → Graph → MCP → LibreChat)`. State which spans are measured (OBO exchange, MCP hop, Graph round-trip). Reference the measurement plan (logs, traces, or a future observability hook — PRE-RESEARCH-013).

- **HIGH** Restart-only deploy causes synchronized OBO token-cache cold start (thundering herd on Entra)
  - Evidence: REQ-014: "Restarting the API (`./prod.sh restart api`) is the only LibreChat-side action needed after `librechat.yaml` changes." PERF-003: "`GraphTokenService` caches the per-user Graph token under `${user.openidId}:${scopes}` so consecutive tool calls within a single conversation reuse a single OBO exchange." The cache is in-process; `./prod.sh restart api` evicts it for every user simultaneously.
  - Risk: After every restart, the first M365 tool call per active user triggers a JWT-bearer OBO exchange to Entra (synchronous external call on hot path, no warm cache). For N concurrent users mid-conversation, this is N simultaneous round-trips to `login.microsoftonline.com`. Entra throttles per-app OBO requests; under burst, some users will see auth errors that look like REQ-015 missing-token errors but are actually transient throttling. Spec calls out no circuit breaker, no request coalescing (if two requests for the same user race, both will OBO-exchange), and no backoff strategy beyond MCP's connect-time circuit breaker.
  - Resolution: Add a non-functional requirement: bound concurrent OBO exchanges (semaphore or in-flight request coalescing keyed by `${user.openidId}:${scopes}`). Document expected post-restart OBO QPS and Entra throttling thresholds. Optionally pre-warm cache for active sessions on startup, or persist the OBO cache in Redis so restart preserves it. Specify error-classification: distinguish Entra throttle (retryable) from genuine missing-token (REQ-015).

- **MEDIUM** Token cache key shape leak: changing `OPENID_GRAPH_SCOPES` orphans every cached token
  - Evidence: MODULE-003 Hides: "OBO scope-set cache-key implications inside `GraphTokenService` (cache key is `${user.openidId}:${scopes}`, so the scope string is part of the cache contract; changing it invalidates cached tokens)." REQ-009 mandates updating `OPENID_GRAPH_SCOPES`; future phase-2 scope additions (Mail.ReadWrite etc.) will re-key the cache.
  - Risk: (a) Anti-pattern "Token cache key shape leak": the cache key includes the full scope string, so any non-identical scope-set serialization (different order, whitespace, case) produces a cache miss. The spec does not specify normalization (sorting, lowercasing, trimming). (b) Every phase-2 scope expansion is a cache-wide invalidation event — the same thundering-herd profile as REQ-014 restart. (c) Per-user multi-conversation flows with subtly different scope subsets (e.g., a future per-tool scope-pinning feature) would produce N cache entries per user.
  - Resolution: Specify scope-key normalization: sort + lowercase + comma-join the scope list before hashing into the cache key. Document that scope changes are cache-invalidating and should be coordinated with the restart-OBO mitigation above. Optionally: cache the scope-set independent of presentation order using a deterministic hash.

- **MEDIUM** Cold-start budget (5s) is asserted, not measured; `initTimeout: 150000` is 30x the budget
  - Evidence: PERF-001: "Cold-start latency for the first MCP call after `mcp-m365` restart is allowed up to 5 seconds (Softeria server + lazy tool registration). `initTimeout: 150000` ms is set to absorb this comfortably." REQ-018: `condition: service_started` + `initTimeout: 150000`.
  - Risk: Anti-pattern "Cold start tolerance unbounded": 150s is a retry/timeout budget 30× the stated 5s cold-start. If actual cold-start drifts upward (Softeria adds tools, image grows, alpine cold cache, network DNS), the gap means a degraded sidecar can hang LibreChat MCP init for 2.5 minutes before failing. During this 150s window, what happens to user tool calls that route to `Microsoft365`? Spec doesn't say — likely they queue or time out per `timeout: 45000`, but the interaction between API-container readiness and MCP init is unspecified. `service_started` only waits for the container to start, not for the MCP endpoint to bind.
  - Resolution: Tighten `initTimeout` to ~15000-30000 ms once measured cold-start is known (drop after OD-1 pin). Add a measurement requirement: log cold-start duration on every `MCPManager` connect; alert if it exceeds 80% of `initTimeout`. Clarify behavior of in-flight tool calls during the 150s window (rejected fast vs. queued). Consider a Docker healthcheck on `/mcp` (or fallback per OD-5) and `condition: service_healthy` instead of `service_started` to eliminate the race.

- **MEDIUM** Unbounded MCP tool surface: 70+ Softeria tools registered per connect, not per use
  - Evidence: REQ-012: "No `--discovery` flag is passed; LibreChat's event-driven lazy tool loading (v0.8.3+) governs which Softeria tools are surfaced to a given conversation." MODULE-001 Hides: "The 70+ Softeria Graph tool implementations…"
  - Risk: Anti-pattern "Unbounded MCP tool surface": LibreChat's "lazy tool loading" controls *surfacing to the model*, but the MCP server still *registers* all 70+ tools on every fresh streamable-http session (this is what `initTimeout` is absorbing). Each tool registration is JSON-schema serialization across the wire. For an agent enabled with `Microsoft365`, the per-conversation cost of fetching the tool list is paid even if only `Mail.Read` is ever used. The spec describes this as a non-issue but provides no measurement: how big is the tool-list response payload? How many tokens does the model see in its tool-list context?
  - Resolution: Measure and document: (a) size of the MCP tool-list response, (b) tool-list registration latency, (c) prompt-token cost of injecting 70+ tool schemas into the model context. If costs are high, recommend Softeria configuration to subset tools (or revisit `--discovery` if it now exists). Add to PERF section: expected steady-state tool count surfaced per conversation, and a budget.

- **LOW** Per-request token-cache TTL and refresh timing not specified
  - Evidence: PERF-003: "When a cached token expires or nears expiry, the service re-runs the JWT-bearer OBO exchange on the next call." MODULE-003 references `GraphTokenService` but doesn't pin TTL.
  - Risk: "Nears expiry" is unspecified. If the refresh trigger is too aggressive (e.g., 30 min before expiry), users pay extra OBO exchanges for no benefit. If too lax (e.g., 30 seconds before expiry), in-flight tool calls can fail mid-flight when the cached token expires between MCP-hop start and Graph reply. No reference to whether Graph token lifetime is 1h (typical) or shorter under conditional access.
  - Resolution: Specify the refresh trigger explicitly (e.g., "refresh when remaining TTL < 5 minutes"). Document Graph token nominal lifetime assumption (1h). Reference where `GraphTokenService` defines this so future readers can find it.

- **LOW** No measurement plan for any PERF requirement
  - Evidence: PERF-001/002/003 use bare numbers ("5 seconds", "<800 ms", "<50 ms") without stating how they're measured, where the data lives, or what triggers an alert.
  - Risk: Performance regressions cannot be detected without a baseline. The Verification Plan smoke tests confirm functional correctness only ("expect a `/me` response") and have no latency assertions.
  - Resolution: Add a "Performance Measurement" subsection to the Verification Plan: list which logs/metrics to scrape (existing LibreChat logs? new traces?), how to compute p50/p95/p99 from them, and what dashboard/alert would catch regression. Reference PRE-RESEARCH-013 if observability work is in the roadmap.
