#### API Contract Findings

- **HIGH** Tool-call contract drift via unpinned Softeria image
  - Evidence: REQ-002 ("installs `@softeria/ms-365-mcp-server` (pinned to a specific version after first successful deploy)"), OD-1 ("First deploy uses `@latest`; immediately after green smoke-test, pin to the resolved version"), implementation step 1 (`Dockerfile` uses `@latest`).
  - Risk: The first deploy ships with a floating `@latest` tag — every `./prod.sh build mcp-m365` between initial deploy and the deferred pin step can silently change the tool list, tool input/output schemas, and `--toon` normalization behavior. Agents that learned to call `messages-list` may discover it renamed or its arguments restructured on a rebuild. Worse, OD-1 is a soft commitment with no enforcement; if the operator forgets the pin step the contract stays unpinned indefinitely. The `Microsoft365` MCP entry has no `version` or schema-hash check on LibreChat's side, so drift is invisible until a tool call fails mid-conversation.
  - Resolution: Make REQ-002 require a concrete version pin from the very first build (resolve Softeria's current stable version during spec finalization and write it into the Dockerfile literal). Promote OD-1 from "deferred to first deploy" to a release gate: no merge of the implementation PR until the Dockerfile contains a resolved semver. Add a verification-plan step that records the exact resolved version in a committed `mcp-m365/VERSION` or similar artifact, so a future `git log` shows when the tool surface changed.

- **HIGH** Bearer token contract underspecified at the LibreChat-to-sidecar boundary
  - Evidence: REQ-004 (`headers.Authorization: "Bearer {{LIBRECHAT_GRAPH_ACCESS_TOKEN}}"`), REQ-007 ("placeholder is resolved by `resolveGraphTokenPlaceholder()` via `GraphTokenService.getGraphApiToken()`"), MODULE-001 Public Interface ("consumes `Authorization: Bearer <graph-token>` per request"), MODULE-002 Public Interface ("Implicit: the `{{LIBRECHAT_GRAPH_ACCESS_TOKEN}}` placeholder contract").
  - Risk: The spec describes the wire format (`Authorization: Bearer <jwt>`) but never specifies what Softeria's server is contractually required to accept. There is no statement about (a) which audience the JWT must target (`https://graph.microsoft.com` vs `api://<client-id>` vs `00000003-0000-0000-c000-000000000000`), (b) what the sidecar does on a malformed/expired/wrong-audience token — does it 401 cleanly, or does Graph 401 surface back through MCP framing? (c) whether the resolver injects an empty string when no Entra session exists (REQ-015 hints at this for local-auth users but doesn't define the wire shape). Without this nailed down, a future Softeria release could change its token validation (e.g., start requiring `aud=api://...`) and silently break every M365 call, or an empty placeholder could ship `Authorization: Bearer ` to the sidecar with undefined behavior.
  - Resolution: Add a REQ between 007 and 008 ("Bearer token contract") stating: (1) the token is a Graph access token with audience `https://graph.microsoft.com` obtained via OBO from the user's OIDC session; (2) the sidecar must treat it as opaque — no local signature validation, only Graph upstream; (3) when `GraphTokenService.getGraphApiToken()` returns null (non-Entra session), the `Authorization` header is omitted entirely, not sent with an empty Bearer; (4) Graph 401 from upstream surfaces as an MCP tool error with a stable error code. Cross-reference this requirement from REQ-015 and REQ-016.

- **MEDIUM** MCP protocol version not pinned
  - Evidence: REQ-004 (`type: streamable-http`), RESEARCH-005 ("Deprecated in MCP spec March 2025, still supported" re SSE; streamable-http "Recommended for new deployments"), no protocol-version field anywhere in the `Microsoft365` entry.
  - Risk: MCP is an evolving protocol (RESEARCH-005 explicitly notes the SSE deprecation in March 2025 and the streamable-http migration). A Softeria release could adopt a newer MCP protocol revision that LibreChat's `MCPManager` does not yet implement — or vice versa. The spec gives no compatibility matrix and no protocol-version handshake check. If MCP introduces a breaking change to streamable-http framing in 2026, both sides will simply fail to negotiate, and the failure mode (per circuit-breaker rules cited in RESEARCH-005: 7 cycles, 45s window) is a long blocked startup, not a clear diagnostic.
  - Resolution: Add an OD or REQ that records the targeted MCP protocol version (e.g., "MCP 2025-06" or whatever rev LibreChat's `MCPManager` implements at spec time), and require the smoke test to log Softeria's reported protocol version. If the sidecar advertises a version newer than what `MCPManager` supports, fail the connect with a logged warning instead of relying on circuit-breaker retries.

- **MEDIUM** Ambiguous error shape for Graph 403 surfacing
  - Evidence: REQ-015 ("clear error to the agent describing the missing token, not a 500"), REQ-016 ("Graph 403 must surface to the agent as a clean tool error, not as a server crash or stuck stream"), Verification Plan negative tests (Missing consent → "403 surfaced as a tool error"; Phase-1 write attempt → "Graph 403, captured cleanly").
  - Risk: Three different requirements (REQ-015, REQ-016, the "Phase-1 write attempt" negative test) all gesture at "tool error" but none defines the wire shape. Is it MCP `{ "isError": true, "content": [...] }`? A thrown exception serialized by `MCPManager`? A specific error code (`InsufficientScope`, `Unauthorized`)? Without a defined shape, the LLM cannot reliably distinguish "you don't have permission for OneDrive" from "the sidecar is down" — both look like a generic tool failure. SPEC-009 PII detection (REQ-019) also flows over this path and needs a stable error shape to avoid attempting redaction on error bodies.
  - Resolution: Define a single error response schema for the three failure modes (no token / missing scope / write attempt) in a new sub-section under Success Criteria. Specify: HTTP status returned by sidecar (or MCP error code in the tool-call response), the error-body JSON shape, the message field convention, and whether Graph's `code` (`Authorization_RequestDenied`, `ErrorAccessDenied`) is preserved verbatim or remapped. Make REQ-015, REQ-016, and the negative tests reference this schema by name.

- **MEDIUM** `serverInstructions` is a prompt-time contract with no drift control
  - Evidence: REQ-004 (`serverInstructions` "names every M365 surface available to the agent"), UX-002 ("`serverInstructions` string … names the M365 surfaces in human terms; the LLM sees this when choosing whether to invoke a tool"), Implementation step 3 (full text inlined), REQ-010 (no `--org-mode`, no Teams write tools).
  - Risk: `serverInstructions` is effectively a contract between the spec author and the LLM at every conversation. The inlined text lists "Outlook mail, Calendar, OneDrive, SharePoint, Excel, OneNote, To Do, Planner, Contacts, and Graph search" and asserts "All scopes are read-only in phase 1". When phase 2 lands (write scopes, `--org-mode` per OD-4) or when Softeria adds/removes a tool family, this text must be updated in lockstep — but the spec has no mechanism tying the `serverInstructions` text to either the actual tool list returned by the sidecar at init time or the scope set in REQ-008. A future scope expansion that forgets to update `serverInstructions` will leave the model believing it's still read-only while it can actually issue writes, or vice versa (model refuses operations it could perform).
  - Resolution: Either (a) add a verification-plan step that diffs `serverInstructions` content against `REQ-008` scopes and `REQ-010` flag set on every PR that touches `librechat.yaml`, or (b) generate `serverInstructions` text from a single source of truth (a constant) that also drives the scope list. Minimally, add a REQ stating "`serverInstructions` must be updated in the same PR as any scope change in REQ-008 or any `--org-mode`/feature-flag change in REQ-010."

- **LOW** Tool naming collision risk under `Microsoft365` group label
  - Evidence: UX-001 ("M365 tools appear under a group label of `Microsoft365` (matching the YAML key)"), RESEARCH-005 ("Softeria … 70+ tools" spanning Mail/Calendar/OneDrive/SharePoint/Excel/OneNote/ToDo/Planner/Contacts/Graph search), no enumeration of how Softeria names individual tools.
  - Risk: With 70+ tools surfaced under a single group label, name collisions become possible (e.g., a future MCP server also exposes a `search` or `list` tool). LibreChat's agent builder appears to use the YAML key as a namespace, but the spec does not state whether tool names are flat (`search`) or namespaced (`Microsoft365__search`). If flat, a future `mcpServers.Slack.search` would conflict. The spec also offers no allowlist/denylist for which of the 70 tools should be exposed in phase 1 — the agent builder will surface all of them, including ones (e.g., Excel charts, OneNote sections) that may not be in the intended phase-1 surface area despite being read-only.
  - Resolution: Add a clarifying note to UX-001 specifying tool namespacing convention (likely `Microsoft365_<tool>` or whatever `MCPManager` does today — confirm against existing `docs.mcp.cloudflare.com` integration). Consider adding an OD or REQ defining whether phase 1 ships with all 70+ Softeria tools or a curated subset (perhaps via a Softeria `--tools` filter flag if available).

- **LOW** `mcpSettings.allowedDomains` entry is a bare hostname (low-grade contract weakness)
  - Evidence: REQ-005 ("bare-hostname entry `mcp-m365`"), OD-2 resolution ("`isDomainAllowedCore` matches hostname-only allowlist entries"), Implementation step 3.
  - Risk: Allowing a bare hostname (no scheme, no port) means any sibling container that responds on a port named `mcp-m365` would match — and inside `caddy_net` and `default` networks this is unlikely but not impossible if Compose service names ever collide with a future deployment. There is no protocol pin (anyone could swap the entry from `http://mcp-m365:3000/mcp` to `https://mcp-m365:443/...` without an allowlist update). For an internal allowlist this is a low-grade contract weakness, not a security hole, but it is a stricter-than-necessary allowlist semantics that the spec inherited from existing code rather than designed deliberately.
  - Resolution: Note in REQ-005 that the choice of bare hostname (vs `http://mcp-m365:3000`) is a consequence of existing `isDomainAllowedCore` semantics, not a spec preference. If `extractMCPServerDomain` ever changes to require origin matching, the allowlist entry must be updated — flag this dependency.
