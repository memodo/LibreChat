#### Reliability Findings (Iter 3)

- **M** Combined healthcheck collapses liveness/readiness back into one signal
  - Evidence: REQ-018 acknowledges Compose has "a single `healthcheck:` slot per service" and Implementation Plan §2 ships a single combined `test:` command (`nc -z localhost 3000 && (wget -q --spider /health || /mcp)`) with `retries: 8` and `start_period: 90s`. REL-003 then claims "A sidecar that is process-responsive but cannot serve MCP … fails ONLY the readiness probe and is NOT restarted" — but `restart: on-failure` + `restart_policy.condition: on-failure` is wired to the *combined* healthcheck. The named split is semantic only; Docker has no way to know which sub-test failed.
  - Risk: Liveness/readiness conflation is reintroduced in implementation. A stalled Graph upstream (which only `wget --spider /mcp` would detect) becomes indistinguishable from a wedged event loop, triggering the REL-003 restart cascade against an otherwise-healthy process while in-flight requests are dropped. This is precisely the anti-pattern REQ-018 names but does not eliminate. Also: `retries: 8 × interval: 10s = 80s` detection latency contradicts REL-003's stated "~50s detection" math (which assumed `retries: 5`).
  - Resolution: Either (a) make the combined `test:` script `exit 1` on liveness failure and a *distinct non-failing* exit (or a sentinel file/log) on readiness-only failure with `restart_policy` actually distinguishing them — which Docker cannot — OR (b) honestly document this as "we have one healthcheck; the named 'liveness/readiness split' is a documentation artifact and a slow Graph upstream WILL cause restarts after 80s" and tighten `restart_policy.max_attempts` accordingly. Reconcile the REL-003 "~50s" figure with the actual `retries: 8` setting.

- **M** REL-002 7-cycle / 45s circuit breaker is asserted as a framework default but never inspected
  - Evidence: REL-002 states "LibreChat's existing reconnect behavior — max 7 cycles, 45s window, exponential backoff — governs `Microsoft365` server reconnection. This is a `@librechat/agents` framework default." No file/line reference is given for the actual implementation, and the spec never confirms these numbers exist in the current dependency. REQ-027 piggybacks on these values for the deterministic-failure short-circuit budget ("do not consume the 7-cycle / 45s budget"). The regression test "that pins the current values" is described but not specified — what does it import, what does it assert?
  - Risk: If the framework defaults differ (or were tuned in a recent `@librechat/agents` bump), the entire RFC-001/RFC-002 budget calculation is wrong and the deterministic-failure short-circuit may already be implicitly bypassed or amplified. The circuit-breaker contract is effectively "implicit" — the named anti-pattern (#6 Circuit-breaker implicit) is partially present.
  - Resolution: Add a concrete file-path reference (e.g., `node_modules/@librechat/agents/.../reconnect.ts:NN` or the equivalent in `/home/danny/agentus`) confirming the 7-cycle / 45s / exponential-backoff values, and specify the regression test (e.g., "import `MCPReconnectConfig` and assert `{ maxAttempts: 7, windowMs: 45000, backoff: 'exponential' }`"). Without this, REL-002 is an assertion not a contract.

- **L** Bounded-queue cancellation semantics on outer MCP timeout are unspecified
  - Evidence: REQ-024 specifies a 30000 ms queue-wait timeout that emits `Throttled` before the 45000 ms outer MCP timeout. But the spec does not say what happens when a queued call has *already moved to in-flight* and the outer MCP `timeout: 45000` fires while waiting on Graph — does the in-flight slot release? Is the request cancelled at the Softeria layer? If not, a stuck in-flight slot blocks queue progress indefinitely until the underlying Graph socket times out (REQ-025: 30000 ms target, but contingent on Softeria honoring it; the spec acknowledges this may need a proxy).
  - Risk: Bulkhead leak — a hung in-flight call can hold one of the 4-per-user slots past the outer MCP timeout window. Repeated occurrences silently shrink the effective per-user concurrency. Tests §17 covers queue-cap and queue-wait paths but not the in-flight-leak path.
  - Resolution: Specify that on outer MCP timeout the in-flight slot is released and the underlying Softeria call is cancelled (or, if cancellation is not supported, that the slot is forcibly released after `timeout + grace` and any late response is dropped). Add a negative test: stall Graph beyond 45s, assert the freed slot accepts a new call before the original returns.

- **L** "Stuck-stream" negative test relies on `docker pause` only — does not cover slow-loris / chunked-response stall
  - Evidence: Negative test "Sidecar hung but up (REL-003)" uses `docker pause mcp-m365`, which freezes the entire process. The realistic hung-upstream failure is a sidecar that accepts the request, opens an SSE/streamable-http response, and then stalls mid-stream (Graph latency spike, half-open TCP). The verification plan does not exercise this path.
  - Risk: Anti-pattern #10 "Smoke-test absent for failure path" — the most common real-world hung-stream mode (slow trickle, no FIN) is uncovered. The error schema's `UpstreamUnavailable` path is unproven for chunked-response stalls.
  - Resolution: Add a negative test using a mock upstream (or `toxiproxy`-style fault injection on the `default` Docker network) that holds the connection open with no data after the first byte. Assert the 45000 ms timeout fires, the SSE stream closes cleanly, and the slot is released (ties to the previous finding).
