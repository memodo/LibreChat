## Findings by Specialist

#### Security Findings (Iter 3)

- **MEDIUM** OD-10 hostname-uniqueness CI grep is narrower than REQ-031 and misses `networks.*.aliases` collisions
  - Evidence: OD-10 (line 302) — `grep -rn 'container_name: mcp-m365\|hostname: mcp-m365' docker-compose*.yml`. REQ-031 (line 135) — `grep -rn '\bmcp-m365\b' docker-compose*.yml | grep -E 'container_name|hostname|aliases'`.
  - Risk: A malicious or accidental sibling service that registers `networks.caddy_net.aliases: [mcp-m365]` (Docker honors aliases as DNS) would pass OD-10's gate but be caught only by REQ-031's broader grep. With bare-hostname allowlist (SEC-008 / REQ-005), this gives the colliding service Graph Bearer tokens (confused deputy via internal-DNS hijack). The defense-in-depth control that compensates for `isDomainAllowedCore`'s hostname-only matching is therefore weaker than the spec asserts.
  - Resolution: Align OD-10 (line 302) verbatim with REQ-031 (line 135) — include `aliases` (and `networks.*.aliases:` YAML key) in the grep alternation. Also assert that `mcp-m365` resolves to exactly one container at runtime (`docker compose exec api getent hosts mcp-m365 | wc -l` ≡ 1) as a deploy-time smoke test in Verification §1.

- **MEDIUM** `node:22-alpine` base image is not digest-pinned — Dockerfile supply-chain gap
  - Evidence: Implementation Plan §1 (line 311) — `FROM node:22-alpine` (mutable tag). Future Work (line 538) — "Pin Node base image to a digest" listed as phase-2, not phase-1.
  - Risk: REQ-002 carefully pins `@softeria/ms-365-mcp-server` to a semver + tarball SHA-256, but the base image is a moving tag. A rebuild on the prod host (`./prod.sh build mcp-m365`) can silently pull a different `node:22-alpine` digest containing modified system binaries or a backdoored npm/node — bypassing the entire REQ-002 supply-chain ceremony. This contradicts the spec's "release-gate Dockerfile integrity" posture.
  - Resolution: Promote digest pinning from Future Work to REQ-002 / OD-1: Dockerfile MUST use `FROM node:22-alpine@sha256:<digest>` with the resolved digest recorded as a comment alongside the Softeria integrity hash. The same release gate language ("no merge until present") applies.

- **LOW** REQ-023 correlation-ID format leaks internal-identifier topology to Microsoft Graph activity logs
  - Evidence: REQ-023 (line 122) — `client-request-id` value is `${conversationId}:${messageId}:${toolCallId}`. SEC-004 (line 142) excludes correlation-id from the redaction list (it IS logged on the LibreChat side).
  - Risk: Microsoft retains `client-request-id` in Graph activity logs per their retention policy. Memodo's internal conversation/message ID graph (cardinality, churn, per-user volume) becomes derivable from those logs by anyone with Graph activity-log access (Microsoft personnel, future tenant-admin, subpoena). These IDs are not PII but they reveal LibreChat usage shape per user. Privacy & Compliance Scope (line 199) commits to data minimization at the tool boundary; identifier minimization is the symmetric control.
  - Resolution: Amend REQ-023 to send a one-way HMAC-truncated derivative (`HMAC-SHA256(server-secret, conversationId:messageId:toolCallId)`, truncated to 16 hex chars) as the outbound `client-request-id`, and store the mapping in LibreChat-side audit metadata only. Reconstruction (SEC-004 join) still works because the mapping is held LibreChat-side. Alternatively, document the deliberate trade-off in SEC-004 with an explicit "internal IDs leak by design — accepted because they are non-PII" note + DPO-equivalent sign-off folded into OD-6.

- **LOW** REQ-020 missing nbf (not-before) and tid (tenant-id) explicit checks
  - Evidence: REQ-020 (lines 108-115) validates `aud`, `iss` (pattern includes tenant), `ver`, `oid`, `upn`/`preferred_username`, `appid`/`azp`, remaining lifetime.
  - Risk: `iss` regex matches the tenant in the URL path but `tid` claim is not explicitly cross-checked. A token with a spoofed `iss` URL containing the Memodo tenant but `tid` belonging to a different tenant would pass (unlikely in practice — Microsoft signs `iss`, but defense-in-depth costs nothing). `nbf` skew can allow a future-dated token to be emitted; remaining-lifetime ≥60s does not guard against `nbf > now`.
  - Resolution: Extend REQ-020 (line 108-115) to add: `tid === <Memodo-tenant-id>` (extracted from iss for cross-check) and `nbf ≤ now + clockSkew (60s)`. One additional line each in the invariant list.

Checked: hardcoded secrets in examples (none — `.env.prod` shows scope list only); authz on state-changing endpoints (no state-changing endpoints in phase 1 per SEC-003 read-only); input validation at trust boundary (REQ-020 JWT invariants validated before emission, header omitted on null); IDOR (OBO scopes calls to user's own data per SEC-004); secret/PII logging (SEC-007 negative-assertion in Verification §6, §12; covers Authorization headers, payload bodies, query-string filters, mail subjects, recipients, attendees, file names); crypto primitives (none introduced — token is opaque to sidecar per REQ-020 last bullet); rate limiting (REQ-024 per-user 4 / per-conversation 8 with bounded FIFO and Throttled emission before outer timeout); SSRF allowlist (SEC-002 internal DNS only, SEC-008 inherited weakness named, SEC-006 egress to graph.microsoft.com:443 only is now a release gate via OD-6); token scope vs least-privilege (REQ-008 broad-scope rationale documented inline with 4 compensating controls); BYOT confused-deputy (REQ-003 / SEC-001 no tokens at rest, REQ-006 BYOT-only, REQ-020 rejects app-only/.default tokens via appid check); image supply chain (REQ-002 semver + tarball SHA-256 + VERSION artifact + OD-1 release gate — base-image digest gap flagged above); REQ-026 resource limits (256m/0.5 CPU appropriate); SEC-006 escape-hatch tightened (OD-6 release gate; "documented residual risk" fallback explicitly REMOVED at line 378 / 298).

#### Performance Findings (Iter 3)

- **H** Queue-wait timeout + Graph inner timeout SUM exceeds outer MCP timeout (cascading-timeout discipline violated)
  - Evidence: REQ-024 sets queue-wait timeout at 30000 ms; REQ-025 sets Softeria's inner Graph HTTP timeout at "target: 30000 ms"; REQ-004 sets outer MCP `timeout: 45000`. A call dequeued at queue-wait≈29s and then performing a Graph round-trip taking ≈30s totals ≈59s end-to-end — 14s past the 45s outer MCP timeout. REQ-024's stated guarantee ("emit `Throttled` BEFORE the outer MCP timeout fires") only holds for calls that time out *in the queue*; calls that just barely escape the queue and then hit a slow Graph response will surface as `UpstreamUnavailable` (outer-timeout class) rather than the correct class, exactly the failure mode REQ-024 says it prevents.
  - Risk: Tail-latency error-class confusion under load — agents see `UpstreamUnavailable` (suggesting retry/backoff) when the true cause is internal saturation (suggesting Throttled + `retryAfter`). REL-002's circuit breaker keys off `UpstreamUnavailable`, so misclassification could trip the breaker on what is really a self-inflicted throttle. Also: outer-timeout-fired calls leak the inner Graph socket past 45s — REQ-025's whole point was to prevent that.
  - Resolution: Make the budgets additive: either (a) queue-wait ≤ (outer MCP timeout − inner Graph timeout − MCP hop budget) = 45000 − 30000 − ~500 = ~14500 ms, OR (b) raise outer MCP timeout to ≥ (queue-wait + inner-Graph + MCP-hop) ≥ 62000 ms, OR (c) reduce queue-wait to ≤14000 ms. Add an explicit invariant to REQ-025: `queue_wait_max + graph_inner_timeout + mcp_hop_budget < outer_mcp_timeout`. Bake the inequality into a unit test alongside the REL-002 7-cycle/45s pin.

- **M** REQ-021 single-flight does not specify retry/backoff scope for transient 429 — re-stampede risk
  - Evidence: REQ-021: "Error classification: distinguish Entra HTTP 429 (retryable with backoff and jitter) from a genuine missing-token / consent-denied failure." OD-7 specifies the `Map<cacheKey, Promise<TokenResponse>>` populated before `await`, cleared in `finally`. The spec does not say WHERE backoff lives. If the in-flight promise rejects on 429 and every concurrent caller awaiting it sees the rejection, each caller then independently retries — producing a fresh K-caller stampede that single-flight just prevented. The `finally`-clear semantic guarantees the next caller after a 429 retries from a cold slot, so failure-mode stampedes are not bounded.
  - Risk: Thundering herd reappears on Entra-side throttling (worst at API restart, scope rotation, or Entra incidents). Defeats PERF-003's "one OBO exchange per (user, scope-set) per cache TTL" property exactly when Entra is least healthy.
  - Resolution: Specify that backoff lives INSIDE the single-flight call — the in-flight promise itself retries with jittered backoff (e.g., up to 3 attempts, base 200ms, full jitter) before rejecting. Concurrent callers ride out the retry as a single coalesced operation. Add a unit test: with the upstream stubbed to return 429 twice then 200, K=10 concurrent callers observe exactly ONE successful resolve and (≤3) Entra calls total, not (≤3 × K).

- **M** PERF-003 token-refresh threshold (<5min remaining) collides with REQ-024 max queue-wait
  - Evidence: PERF-003 refreshes at "remaining TTL less than 5 minutes (not on expiry, to avoid in-flight failures between cache check and Graph round-trip)." Token is read from cache at request entry (LibreChat → MCP). REQ-024 allows a queue-wait of up to 30s plus a Graph round-trip of up to 30s. A call entering at TTL=5min01s passes the refresh check, sits in the queue for 30s, then incurs a 30s Graph round-trip — token expires mid-Graph-call. Surfaces as Graph 401, not retried within the request lifecycle.
  - Risk: Sporadic, hard-to-reproduce 401s on long-tail queued calls; user sees `Unauthenticated` for what is really a budgeting bug. Not catastrophic (read-only, idempotent retry by user works), but pollutes the error-class distribution and confuses on-call.
  - Resolution: Raise the refresh threshold to ≥ (queue-wait-max + graph-inner-timeout + safety) = 30 + 30 + 30 = ~90s minimum, or restructure so the token is re-checked (and refreshed if needed) at the moment of header emission — i.e., AFTER dequeue, not at request entry. Document the chosen point in PERF-003.

- **M** No cache layer for read-heavy Graph responses; every tool call is a fresh round-trip
  - Evidence: PERF-002 budgets p50≤1s / p95≤3s / p99≤8s for end-to-end tool calls, but the only cache layer in the spec is the OBO token cache (PERF-003). Sidecar is stateless (REQ-003). No request coalescing on tool-result level. A read-heavy phase-1 surface (Mail, Files, Sites, Contacts) repeatedly invoked within a single conversation (e.g., agent paginating or refining a search) re-hits Graph on every call, paying the full p95.
  - Risk: Tail latency dominated by Graph round-trip; PERF-002 p95≤3s budget will fail to hold under realistic agent workflows (refine-and-retry loops) where the same underlying entity is fetched 3-5x per conversation turn. Misses a clear optimization for read-heavy operations.
  - Resolution: Either (a) explicitly call out "no Graph-result cache in phase 1; freshness preferred over latency; PERF-002 budgets measured on single-call basis, not amortized" — making the design choice explicit and bounding the budget interpretation, OR (b) add a short-lived (60-120s) per-(user, endpoint, params-hash) result cache in the OBO/MCP layer with a documented invalidation contract. Option (a) is acceptable for phase 1 if the budget is honest about it.

- **L** PERF-004 tool-list prompt-token cost is recurrent per conversation, not a one-time gate
  - Evidence: PERF-004 measures "(c) the prompt-token cost of injecting the resulting tool schemas into the model context per conversation. Targets to verify at first deploy: ... tool-schema prompt-token cost < 10K tokens." Gate is "On breach of any target: rollout is BLOCKED". Recurrence is not budgeted as ongoing cost — it's a one-time pre-rollout check.
  - Risk: With 70+ Softeria tools, a per-conversation 10K token preamble at scale (N conversations × M turns) is a recurring inference cost line item. If Softeria adds tools in a minor version bump (REQ-002 version bump), prompt-token cost can creep upward silently; only re-measured "on every Softeria version bump" per PERF-004, which is correct but not enforced as CI.
  - Resolution: Add a CI check (or a doc'd manual step) that diffs the tool-list payload size + tool-count on every PR that bumps `mcp-m365/VERSION`. Optionally express the prompt-token target as a per-conversation budget × expected-conversations-per-day to make the ongoing inference cost legible to product.

- **L** PERF-001 cold-start alert threshold (80% of `initTimeout: 150000` = 120s) is far above the stated target (5s) — too lax to be useful
  - Evidence: PERF-001: "an alert fires if duration exceeds 80% of `initTimeout`. `initTimeout: 150000` is the initial absorbing budget; it MUST be tightened to ≤30000 ms once measured cold-start is confirmed stable across 10 restarts." Until tightening, the alert fires only at 120s — 24x the 5s target. A cold-start regression from 5s to 60s (a real degradation) would not alert.
  - Risk: A meaningful cold-start regression sits undetected for the entire pre-tightening window (weeks 1-4 by PERF-001's manual measurement cadence). The alert is theatrical until `initTimeout` is tightened.
  - Resolution: Define the alert relative to the BASELINE in `mcp-m365/perf-baseline.json`, not `initTimeout`. E.g., "alert if cold-start p95 > 2× baseline p95 OR > 10s, whichever is lower." This is consistent with the "≥50% regression vs baseline blocks deploy" rule already in PERF-001 — apply the same standard to the runtime alert.

- **Checked & acceptable**
  - REQ-021 single-flight contract (Map shape, populate-before-await, finally-clear, K=10 unit test) — well-specified.
  - REQ-022 scope-key normalization algorithm (`split(/[,\s]+/).map(trim+lowercase).filter(Boolean).sort().join(',')`) — fully specified with unit-test pin.
  - REQ-026 resource limits (256m/0.5 CPU, 128m/0.1 reservations) — plausible for a streamable-http proxy.
  - REL-003 hung-but-up handling and bounded restart policy (`on-failure:5` over 5min window) — sound.
  - REQ-027 deterministic-failure short-circuit (no retry budget consumed) — prevents wasted reconnect cycles.
  - PERF-002 measurement spans (OBO duration, MCP hop, Graph round-trip) clearly enumerated.
  - Verification Plan §Performance methodology (log scrape, p50/p95/p99, 7-day window) — acceptable for phase 1; observability automation rightly deferred to PRE-RESEARCH-013.

#### API Contract Findings (Iter 3)

Scope of fresh re-evaluation: REQ-020 Bearer/JWT invariants, Error Response Schema (canonical envelope, `code` enum, `isError` placement), REQ-027 (MCP protocol pin + deterministic-failure short-circuit), REQ-028 (`serverInstructions` drift control: version marker + SHA-256 + scope-surface grep), REQ-024 (queue-bound + `Throttled`/`retryAfter`), REQ-023 (correlation-ID propagation), REL-001 (idempotency contract for phase-2 writes), UX-001 (tool-namespacing `Microsoft365_<tool>` collision avoidance), REQ-031 / OD-10 (hostname uniqueness as bare-allowlist compensating control), OD-1 (supply-chain pin release gate), OD-9 (protocol version literal release gate).

- **[M]** `code` enum is closed but extensibility policy is unstated
  - Evidence: Error Response Schema lists seven canonical `code` values (`Unauthenticated`, `InsufficientScope`, `WriteForbidden`, `Throttled`, `UpstreamUnavailable`, `SidecarUnavailable`, `ProtocolMismatch`). No statement governs how a future `code` (e.g., phase-2 `ConflictWrite`, `PreconditionFailed`, `NotFound`) is added without breaking agent-side handlers that may switch on the enum. No "unknown → treat as `UpstreamUnavailable`" client-fallback rule is given.
  - Risk: When phase-2 adds write tools (REL-001 mentions idempotency keys for writes), a new `code` value will appear. Agents and any LibreChat-side tool-error renderers that exhaustively switch on `code` will silently miss the new class, surfacing it as an unrecognized error string and possibly confusing retry logic in the agent loop. This is a "breaking change dressed as addition" trap.
  - Resolution: Add one paragraph to the Error Response Schema: (a) `code` is an OPEN enum — new values may be added in any minor; consumers MUST treat unknown values as a generic non-retriable error and surface the `message` field; (b) the four pairs that DO drive retry behavior (`Throttled` → retry with `retryAfter`; `UpstreamUnavailable` → bounded retry per REL-002; `Unauthenticated`/`InsufficientScope`/`WriteForbidden`/`ProtocolMismatch`/`SidecarUnavailable` → NO automatic retry) are STABLE and any change to these semantics is a breaking change requiring a spec amendment. Optionally pin this with a Verification §8 test that asserts the seven canonical values' retry classification.

- **[M]** REQ-024 `Throttled` payload field contract underspecified for the rate-limit (vs. Graph 429) path
  - Evidence: REQ-024 says "Graph HTTP 429 responses from upstream are surfaced to the agent within the same schema with `code: "Throttled"` and the `Retry-After` value preserved when present." The Error Response Schema lists `retryAfter` as "present only for code='Throttled'". But the LibreChat-side queue-wait-timeout path (also surfaces `Throttled` with `retryAfter: 5` per REQ-024 bullet 2) does NOT have an obvious wire signal that distinguishes it from a Graph-originated 429 (which carries `graphCode`/`graphMessage`). The agent cannot tell whether `retryAfter: 5` is an upstream-attested wait or a LibreChat-internal guess.
  - Risk: Agent retry behavior on `Throttled` may over-retry against a still-saturated upstream because it cannot distinguish "Graph said retry in 5s" from "LibreChat queue timed out, guess 5s". Phase-2 write tools (REL-001) would compound this — a retry on a write with a bogus `retryAfter` is the precise scenario where idempotency keys earn their keep, and the contract drift starts here.
  - Resolution: Add a non-required field `throttleSource` to the JSON envelope: `"graph_429"` when surfaced from upstream (and `graphCode`/`graphMessage` populated), `"librechat_queue"` when surfaced from REQ-024 queue-wait-timeout, `"librechat_concurrency_cap"` when surfaced from REQ-024 in-flight cap. Specify that `retryAfter` is authoritative ONLY when `throttleSource === "graph_429"`; otherwise it is a hint. Verification §17 already exercises this path — extend it to assert `throttleSource` is set on the queued-timeout case.

- **[L]** REQ-020 JWT-invariant failure mode is contractually clear but error-class collision with `Unauthenticated` swallows two distinct causes
  - Evidence: REQ-020 says "emission MUST throw `InvalidGraphToken` if any invariant fails — surfaces as `Unauthenticated` to the agent". The Error Response Schema then defines `Unauthenticated` as "no valid Entra session / token resolver returned null (REQ-015)". These are two distinct conditions — (a) no token at all (local-auth user / non-Entra session); (b) a token exists but fails an invariant (wrong `aud`, wrong `iss`, expired-ish, wrong `appid`) — collapsed onto the same wire code.
  - Risk: Operationally, (a) is benign (expected for local-auth users; UX should hide M365 tools), but (b) is a signal of a misconfigured Entra app, a cross-tenant token leak, or a token-minting regression — exactly the case where ops want a loud signal and a dashboard. Collapsing both onto `Unauthenticated` loses that signal at the agent boundary; operators must dig in server logs to disambiguate.
  - Resolution: Either (a) add a sibling `code: "InvalidToken"` to the canonical enum, reserved for REQ-020 invariant failures, and keep `Unauthenticated` for "no token at all"; OR (b) keep the single `code` but require that `message` distinguish the two cases verbatim AND that a structured log event (with `event: "graph.token.invariant_failure"` and the specific invariant) be emitted server-side on path (b) so dashboards can alert. The current spec says `surfaces as Unauthenticated` without choosing.

- **[L]** REQ-027 protocol-version-literal slot is parameterized but a downgrade-tolerance / pin-policy clause is missing
  - Evidence: REQ-027 pins protocolVersion to "the LibreChat v0.8.4-rc baseline" and the implementation PR fills the literal (OD-9). Deterministic-failure classification covers MISMATCH. There is no statement on what happens when a sidecar advertises an OLDER but still-supported revision (negotiation), nor what happens when MCPManager itself is upgraded (e.g., LibreChat picks up `@librechat/agents` with a new protocolVersion default) — does the pin floor, the pin ceiling, or both, change?
  - Risk: Tool-call contract drift via unpinned upstream — exactly the named anti-pattern. A silent `@librechat/agents` minor bump that changes the advertised protocolVersion will pass REQ-027's "advertised version matches pin" only if the pin literal is updated in lockstep; otherwise CI will fail and the spec ambiguity (is this a breaking change for `Microsoft365` or not?) will surface at deploy time, not at PR time.
  - Resolution: Add one line to REQ-027: "If MCPManager's protocolVersion changes via a `@librechat/agents` upgrade, SPEC-014 MUST be re-evaluated as a versioning event — the pin literal in `librechat.yaml` and `mcp-m365/VERSION` is updated in the SAME PR as the dependency bump, and Verification §8 asserts the new pin before merge."

- **[L]** UX-001 tool namespacing convention is stated but not enforced for Softeria-emitted tool names
  - Evidence: UX-001 says "individual tool names use the `Microsoft365_<tool>` prefix to prevent collision with other MCP servers (e.g., a future `Slack.search` would not collide with a Microsoft365 search tool)." But Softeria's `@softeria/ms-365-mcp-server` controls its own tool names on the wire; LibreChat does NOT rewrite tool names emitted by an MCP server. The convention is enforceable ONLY if Softeria's tools already happen to use that prefix.
  - Risk: Tool naming collision (named anti-pattern). If a phase-2 MCP server (e.g., a hypothetical Slack MCP) emits a `search` tool, and Softeria emits a bare `search` tool, the agent prompt will see two tools with identical names and the model's tool selection is non-deterministic. Worse, switching servers across releases can change tool identity if names alias.
  - Resolution: Either (a) confirm in OD-9 / implementation PR that Softeria's tool names already carry a server-scoped prefix (e.g., they're emitted as `Microsoft365_mail_list` because that's how `@librechat/agents` namespaces tools-by-server) and update UX-001 to say "this is enforced by MCPManager's server-scoped tool-name prefixing"; OR (b) if names are bare, add an implementation note that the `Microsoft365` server label is the de-facto namespace at the agent-builder level and accept that wire-level tool names are governed by upstream — and explicitly note this is a phase-1 acceptance, with a phase-2 follow-up to prefix-mangle tool names if a colliding server is introduced. Either way, the spec should pick one.

- **[L]** Error envelope JSON-in-text encoding is documented but no version field on the envelope itself
  - Evidence: Error Response Schema places structured fields inside `content[0].text` as a JSON-stringified blob with fields `code`/`message`/`graphCode`/`graphMessage`/`correlationId`/`retryAfter`. There is no envelope version field (e.g., `"schemaVersion": 1`) on the JSON blob.
  - Risk: When the envelope evolves (the [M] above suggests adding `throttleSource`; the [L] above suggests adding `InvalidToken` or a structured-log-only divergence), agent-side parsers and tests that strictly schema-validate the JSON blob will break. Adding a version field NOW is cheap; retrofitting it later breaks every consumer that exhaustively validates.
  - Resolution: Add `"schemaVersion": 1` as the first field of the JSON blob in the Error Response Schema example, and add one line: "schemaVersion increments only when fields are REMOVED or semantics change; new optional fields (`throttleSource`, future) are additive and do NOT bump the version. Consumers MUST ignore unknown fields." This matches standard envelope versioning.

#### Reliability Findings (Iter 3)

- **M** Combined healthcheck collapses liveness/readiness back into one signal
  - Evidence: REQ-018 acknowledges Compose has "a single `healthcheck:` slot per service" and Implementation Plan §2 ships a single combined `test:` command (`nc -z localhost 3000 && (wget -q --spider /health || /mcp)`) with `retries: 8` and `start_period: 90s`. REL-003 then claims "A sidecar that is process-responsive but cannot serve MCP … fails ONLY the readiness probe and is NOT restarted" — but `restart: on-failure` + `restart_policy.condition: on-failure` is wired to the *combined* healthcheck. The named split is semantic only; Docker has no way to know which sub-test failed.
  - Risk: Liveness/readiness conflation is reintroduced in implementation. A stalled Graph upstream (which only `wget --spider /mcp` would detect) becomes indistinguishable from a wedged event loop, triggering the REL-003 restart cascade against an otherwise-healthy process while in-flight requests are dropped. This is precisely the anti-pattern REQ-018 names but does not eliminate. Also: `retries: 8 × interval: 10s = 80s` detection latency contradicts REL-003's stated "~50s detection" math (which assumed `retries: 5`).
  - Resolution: Either (a) make the combined `test:` script `exit 1` on liveness failure and a *distinct non-failing* exit (or a sentinel file/log) on readiness-only failure with `restart_policy` actually distinguishing them — which Docker cannot — OR (b) honestly document this as "we have one healthcheck; the named 'liveness/readiness split' is a documentation artifact and a slow Graph upstream WILL cause restarts after 80s" and tighten `restart_policy.max_attempts` accordingly. Reconcile the REL-003 "~50s" figure with the actual `retries: 8` setting.

- **M** REL-002 7-cycle / 45s circuit breaker is asserted as a framework default but never inspected
  - Evidence: REL-002 states "LibreChat's existing reconnect behavior — max 7 cycles, 45s window, exponential backoff — governs `Microsoft365` server reconnection. This is a `@librechat/agents` framework default." No file/line reference is given for the actual implementation, and the spec never confirms these numbers exist in the current dependency. REQ-027 piggybacks on these values for the deterministic-failure short-circuit budget ("do not consume the 7-cycle / 45s budget"). The regression test "that pins the current values" is described but not specified — what does it import, what does it assert?
  - Risk: If the framework defaults differ (or were tuned in a recent `@librechat/agents` bump), the entire RFC-001/RFC-002 budget calculation is wrong and the deterministic-failure short-circuit may already be implicitly bypassed or amplified. The circuit-breaker contract is effectively "implicit" — the named anti-pattern (#6 Circuit-breaker implicit) is partially present.
  - Resolution: Add a concrete file-path reference (e.g., `node_modules/@librechat/agents/.../reconnect.ts:NN` or the equivalent in `/home/danny/agentus`) confirming the 7-cycle / 45s / exponential-backoff values, and specify the regression test (e.g., "import `MCPReconnectConfig` and assert `{ maxAttempts: 7, windowMs: 45000, backoff: 'exponential' }`"). Without this, REL-002 is an assertion not a contract.

- **L** Bounded-queue cancellation semantics on outer MCP timeout are unspecified
  - Evidence: REQ-024 specifies a 30000 ms queue-wait timeout that emits `Throttled` before the 45000 ms outer MCP timeout. But the spec does not say what happens when a queued call has *already moved to in-flight* and the outer MCP `timeout: 45000` fires while waiting on Graph — does the in-flight slot release? Is the request cancelled at the Softeria layer? If not, a stuck in-flight slot blocks queue progress indefinitely until the underlying Graph socket times out (REQ-025: 30000 ms target, but contingent on Softeria honoring it; the spec acknowledges this may need a proxy).
  - Risk: Bulkhead leak — a hung in-flight call can hold one of the 4-per-user slots past the outer MCP timeout window. Repeated occurrences silently shrink the effective per-user concurrency. Tests §17 covers queue-cap and queue-wait paths but not the in-flight-leak path.
  - Resolution: Specify that on outer MCP timeout the in-flight slot is released and the underlying Softeria call is cancelled (or, if cancellation is not supported, that the slot is forcibly released after `timeout + grace` and any late response is dropped). Add a negative test: stall Graph beyond 45s, assert the freed slot accepts a new call before the original returns.

- **L** "Stuck-stream" negative test relies on `docker pause` only — does not cover slow-loris / chunked-response stall
  - Evidence: Negative test "Sidecar hung but up (REL-003)" uses `docker pause mcp-m365`, which freezes the entire process. The realistic hung-upstream failure is a sidecar that accepts the request, opens an SSE/streamable-http response, and then stalls mid-stream (Graph latency spike, half-open TCP). The verification plan does not exercise this path.
  - Risk: Anti-pattern #10 "Smoke-test absent for failure path" — the most common real-world hung-stream mode (slow trickle, no FIN) is uncovered. The error schema's `UpstreamUnavailable` path is unproven for chunked-response stalls.
  - Resolution: Add a negative test using a mock upstream (or `toxiproxy`-style fault injection on the `default` Docker network) that holds the connection open with no data after the first byte. Assert the 45000 ms timeout fires, the SSE stream closes cleanly, and the slot is released (ties to the previous finding).

## Cross-Specialist Observations

Three issues are flagged by two or more specialists at different angles or severities — none collapsed to a single finding (the framings are sufficiently distinct to retain separately) but the convergence is significant:
